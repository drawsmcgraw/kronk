# TTS bench, 2026-11-18 (sprint M20): Piper against Pocket TTS, Chatterbox and Chatterbox-Turbo

**Provisional.** This is the part of the M20 trial that needs no voice clips:
speed, stability, idle GPU and model slowdown with stock or preset voices.
The household listening test and the cloning run wait for Drew's clips; the
verdict on "garbled or extra audio" waits for the listening test. Build
report: `docs/sprint/M20-build.md`. Numbers: `tts_bench_2026-11-18.json`
(summaries and every flagged row). Tool: `scripts/tts_bench.py`, sentences
`scripts/tts_bench_sentences.json` (20 sentences, 6 kinds, written for the
bench).

## What was run

| Engine | Server | Runtime | Voice (no cloning, no reference audio) |
| --- | --- | --- | --- |
| Piper (baseline) | `rhasspy/wyoming-piper:2.2.2`, a second container, production's voice files mounted read-only | CPU (onnxruntime) | `en_US-hfc_male-medium`, as production |
| Pocket TTS, server A | `ikidd/pocket-tts-wyoming` @`9ed4112`, `pocket-tts` 4.0.1 | CPU (torch 2.11.0+cpu, all cores) | preset `alba` (a shipped voice state from the ungated no-cloning weights) |
| Pocket TTS, server C | `MisterEcks/pocket-tts-streaming` @`b9821d3`, same engine and venv | CPU (torch, 4 threads) | preset `alba` |
| Chatterbox | `devnen/Chatterbox-TTS-Server` v2.0.0 (one scratch patch, below) behind `wyoming-openai` 0.9.0, `chatterbox-tts` 0.1.7 | GPU, PyTorch 2.11.0+rocm7.2 on gfx1151 | the model's built-in `conds.pt` |
| Chatterbox-Turbo | same stack, `model.repo_id: chatterbox-turbo` | same | the model's built-in `conds.pt` |

Every engine ran in a sandbox with no network at all (`bwrap --unshare-net`;
Piper: `network_mode: none`), listening on a Unix socket, with
`scripts/tts_bench.py relay` putting it on `127.0.0.1:102xx`. The bench
speaks Wyoming exactly as HA 2026.5.4 does: the streaming sequence when the
server says it streams (the reply as one chunk, as production sends it with
`VOICE_STREAM` off), one `synthesize` otherwise. 20 sentences x 5 reps per
engine; nothing was played.

Scratch patch to devnen's server: its OpenAI route always conditions on a
WAV file (a reference recording); `voice: "builtin"` now passes no prompt,
so the model uses its shipped voice. Two lines, outside the repo.

Chatterbox and Turbo were measured in short sessions (at most 170 s loaded,
then unloaded, then 70 s of idle GPU), because a loaded Chatterbox process
holds the GPU at 100 % (below) and `kronk-memwatch` pushes a phone alert after
five minutes of that. Their first request after each load is a warm-up and
is not counted.

## Model slowdown

`gemma-4-e4b` on `127.0.0.1:11438`, fixed prompt, 128 tokens, temperature 0,
60 s bursts: alone, then while the engine synthesizes the sentence set back
to back. The first ~13 s of any burst run at a boost clock (99 tok/s, then
85), so bursts are compared on the requests that start after 15 s.

| Engine | Alone (tok/s, mean) | While synthesizing | Change | TTS requests in the burst |
| --- | --- | --- | --- | --- |
| Piper | 85.88 | 60.24 | **-29.9 %** | 554 |
| Pocket A | 85.33 | 81.92 | -4.0 % | 32 |
| Pocket C | 85.36 | 87.06 | +2.0 % | 33 |
| Chatterbox | 85.30 | 63.72 | **-25.3 %** | 9 |
| Chatterbox-Turbo | 85.34 | 68.04 | **-20.3 %** | 11 |

This is the worst case: synthesis without pause for the whole burst, which a
household never does. Piper, today's engine, costs the model 30 % under it
(onnxruntime on every core); Pocket C, held to 4 threads, costs nothing.

## Idle GPU

| State | Minutes | GPU busy (mean / max) | Shader clock | Power mean (p95) |
| --- | --- | --- | --- | --- |
| Piper only (baseline) | 19.8 | 0 / 0 % | 600 MHz throughout | 9.19 W (10.04) |
| Pocket A loaded, idle | 59.8 | 0 / 0 % | 600 MHz throughout | 9.35 W (10.06) |
| Chatterbox loaded, idle | 2.6, then unloaded | 100 / 100 % | 2900 MHz throughout | 37.3 W (39.06) |
| Chatterbox-Turbo loaded, idle | 2.3, then unloaded | 100 / 100 % | 2900 MHz throughout | 37.5 W (39.04) |

Pocket C was not given its own hour: it is the same CPU-only runtime (same
venv, `torch+cpu`, no `/dev/dri` or `/dev/kfd` handle in either process),
which cannot touch the GPU. Chatterbox and Turbo reproduce the June
idle-spin exactly: as soon as the last request ends, 100 % busy, clock pinned
at maximum, about 37 W, and no engine time in fdinfo. The trial's guard
unloaded each after 140 s, because memwatch alerts at five minutes and
because every silent hang on record happened with such a spinner resident.
GPU back to 0 % / 600 MHz / 9 W within seconds of each unload.

## Stability

No crash, hang, timeout, refused request or empty reply from any engine in
any run: 100 of 100 per engine in the main runs, plus 12 per engine in the
sentence-chunk runs (Piper, Pocket A, Pocket C), 2 cold-start requests per
engine, and the TTS loops of the slowdown bursts (554, 32, 33, 9 and 11
requests). No OOM or amdgpu fault in the kernel journal; the llama and
Whisper units kept their PIDs with zero restarts. Two failed launches were
the trial's own (a wrong cache path; a socket directory reused), recorded in
the build report. The Chatterbox stack leaves two Python children running
when its sandbox is sent SIGTERM; the driver killed them each time.

## The plan's hard limits

| Hard limit | Pocket A | Pocket C | Chatterbox | Chatterbox-Turbo |
| --- | --- | --- | --- | --- |
| First audio on a short confirmation no more than 0.5 s slower than Piper (Piper p50 0.043, p95 0.062) | **fail** (p50 +0.48 s passes, p95 +0.65 s fails) | pass (+0.02 / +0.01 s) | **fail** (+3.8 / +5.7 s) | **fail** (+3.0 / +3.7 s) |
| First audio on a three-sentence answer 2 s or less | **fail** (p50 1.33 s, p95 2.15 s) | pass (0.065 / 0.068 s) | **fail** (7.2 / 12.9 s) | **fail** (6.5 / 8.1 s) |
| Model tokens per second drop no more than 10 % while both run | pass (-4.0 %) | pass (+2.0 %) | **fail** (-25.3 %) | **fail** (-20.3 %) |
| No garbled or extra audio in 100 sentences | waits for the listening test (stand-in: 1 short `n02`, 9 word suspects) | waits for the listening test (stand-in: 2 short `n02`, 8 suspects) | waits for the listening test (13 suspects) | waits for the listening test (15 suspects) |
| Idle GPU after one hour back to the Piper-only baseline | pass (60 min, identical) | pass (same runtime, no GPU) | **fail** (100 % / 2900 MHz / 37 W within seconds; not left an hour) | **fail** (same) |
| No crash or hang across the full bench | pass | pass | pass (no crash; the GPU spin is under the idle limit) | pass (same) |

Piper itself would fail the slowdown limit under this worst-case load
(-29.9 %); the limit is read as written, and Piper's figure is here so Drew
can weigh it.

## Could each carry M8's streamed reply?

Measured with the reply sent as one chunk per sentence, 0.5 s apart (M8's
dev path), first audio p50 / p95:

- Piper: yes. 0.546 / 0.572 s on three-sentence answers; its sentence
  detector closes a sentence only when the next text arrives, so first audio
  waits for the second chunk.
- Pocket A: no. It concatenates every chunk until `synthesize-stop`, then
  synthesizes the whole reply and sends audio only when done (2.296 / 2.984 s).
  It advertises streaming anyway.
- Pocket C: yes, and sooner than Piper: 0.064 / 0.575 s (it speaks a first
  fragment of 10 characters or more without waiting for the sentence end).
- Chatterbox and Turbo: by code, yes, a sentence at a time
  (`wyoming-openai` cuts sentences as chunks arrive and streams each
  response); not run in sentence-chunk mode. With the whole reply at once,
  their first audio already comes before the end (Turbo, weather: 3.1 s
  first audio, 7.5 s total), but a single sentence takes 3 to 9 s.

## Not stood up

- **The RVC layer** (`xchwarze/wyoming-rvc`): not run. Its job is to give a
  voice the timbre learned from recordings of a person, and its only
  built-in timbres are two singing-voicebank characters trained from their
  voice providers' recordings. That is reference audio of a person, which
  this trial rules out. Ready to try when Drew's clips arrive; it would sit
  in front of Piper and inherit Piper's speed plus its own (claims are for
  NVIDIA GPUs), and its ROCm image is about 15 GB.
- Pocket TTS's third Wyoming server (`araa47/wyoming_pocket_tts` 1.4.11):
  read, not run. It streams audio but not text, so for M8 it sits between A
  and C.

## Provisional recommendation

**Provisional, until the listening test.** No-go for Chatterbox and
Chatterbox-Turbo on this host as it stands: they fail first audio on a short
confirmation (3 to 4 s against Piper's 0.04 s), first audio on a
three-sentence answer (6.5 to 7.2 s against 2 s), the model-slowdown limit
(-20 to -25 %), and the idle-GPU limit, where they reproduce the ROCm
idle-spin that preceded every silent hang on record. The trial can be
repeated when PyTorch's ROCm build for gfx1151 stops spinning at idle and the
models get faster; the bench and the session driver are ready for it.

Pocket TTS with server C (MisterEcks) passes every limit measured so far:
first audio 0.066 s (Piper 0.043 s), no model slowdown, no idle GPU. It is
the only candidate that could go to the listening test as a live option. Two
things to weigh: server C's last commit is March 2026 and it is a single
file maintained by one person; and its confirmations run longer (audio
p50 2.22 s against Piper's 1.87 s and server A's 1.51 s on the same engine:
0.3 s of tail padding plus pacing between fragments), which the listening
test should hear. Pocket A (the most-starred server) fails two latency
limits only because it generates the whole utterance before sending any
audio.

The trade the plan asks to state: the only cloned-voice candidate that is
not slower than Piper is Pocket TTS, and only through server C. Chatterbox's
voice, whatever it sounds like with Drew's clip, costs 3 to 7 s before the
first word, on top of the phase-2 latency work, and a GPU that never idles.

## Listening-test material

`~/kronk-tts-trial/samples/`: 100 WAVs (`<sentence>-<letter>.wav`, rep 1 of
each engine, letters shuffled per sentence, loudness matched to -20 dBFS
RMS), `sentences.txt`, `rating_sheet.md` (one page: naturalness 1 to 5,

key is a separate file, `~/kronk-tts-trial/samples_key.json`. Made with
`scripts/tts_bench.py blind`. Nothing was played.

The cloning run, in short: Drew supplies one consenting speaker per voice
(his own, or a household member's written yes), 10 to 30 s of clean mono WAV
at 24 kHz or more, placed in `~/kronk-tts-trial/clips/`. Pocket TTS needs
the gated `kyutai/pocket-tts` weights for cloning (Drew accepts the terms
with his Hugging Face account; a read token for the one fetch). Output to
`~/kronk-tts-trial/wav/<engine>-clone/` and a fresh blind set; cloned audio
stays on this host and is never committed.

## Corrections after the end-to-end test (2026-11-18)

The independent test (`docs/sprint/M20-e2e.md`) reproduced every table from
the raw files and re-measured Piper and both Pocket servers within 10 % on
the speed figures. It changes no verdict. Read the text above with these:

- "First audio" is the first audio bytes, not the first sound. The Pocket
  streaming server opens with about 0.22 s of silence (Piper 0.04 s), so the
  first audible sound of a short confirmation is about 0.29 s p50 / 0.33 s
  p95 against Piper's 0.08 / 0.11 s: roughly 0.2 s behind Piper, not
  "+0.02 / +0.01 s". The 0.5 s limit still passes, with 0.3 s of margin.
- The model-slowdown bursts compare equal time, not equal work. In one burst
  Piper answered about 500 requests (38 times real time of speech) and the
  Pocket streaming server about 31 (2.6 times). "Piper costs the model 30 %"
  is true of that saturated load only; for one reply Piper holds the cores
  for about 50 ms and Pocket holds four threads for 0.5 to 5 s. This is not
  a reason to loosen the limit.
- The kernel journal has no OOM, fault or reset, but each Chatterbox or Turbo
  teardown logged `amdgpu: Freeing queue vital buffer ..., queue evicted`
  and there were three `kfd_process_wq_release [amdgpu] hogged CPU` warnings.
- The Pocket streaming server starts speaking early only when the first
  sentence has seven words or more; with a shorter first sentence it waits
  for the next chunk, as Piper does.
- The money sentence ("$1,284.50") was misread by Pocket in 4 of 10 of the
  builder's reps and 0 of 4 of the tester's. Listen for it; the remedy would
  be spelling amounts out before the text reaches the engine.
- Before the listening test: the blind set gives Piper away by sample rate
  (22,050 Hz against 24,000 Hz) and Pocket C by 0.5 s of trailing silence.
  `tts_bench.py blind` must resample to one rate and trim edges first.
