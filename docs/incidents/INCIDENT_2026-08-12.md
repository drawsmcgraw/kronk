# Incident 2026-08-12 — silent hang #4; watchdog was dead, host down 5.6 h

**Symptom:** host fully unresponsive (no UI, no network); operator manually
power-cycled at ~12:22. Fourth occurrence of the silent-hang signature from
`INVESTIGATION_2026-06-09_hangs.md` (journal stops mid-stream, no panic, no
error of any kind). First occurrence where the box did **not** self-recover —
the hardware watchdog installed on 6/9 turned out to be dead (see below).
Total outage 06:46 → 12:22 (~5.6 h): HA, voice, and all Kronk services down.

## Timeline (2026-08-12, EDT)

- **06:06:52** — apt-daily-upgrade runs: "No packages found" (rules out
  update activity; note the kernel *did* change across the incident —
  6.17.0-41 was installed by unattended-upgrades on **7/21** and sat staged;
  the hang happened on 6.17.0-40, today's power-on booted -41).
- **06:12:59** — fwupd-refresh: metadata only.
- **06:40:02** — last sysstat sample: **completely healthy.** 97.7 % idle,
  load 1.2, 47 % mem used, zero swap activity, zero blocked tasks. No
  degradation curve whatsoever.
- **06:44:28** — NetworkManager dips to CONNECTED_SITE, back to
  CONNECTED_GLOBAL at 06:44:29 (connectivity-check blip on `enp191s0`;
  noted, not implicated — WiFi/mt7925 was DOWN the whole boot).
- **06:45:22** — last gpu-mem-export run logged (user journal was lost
  beyond this point — file found corrupted on reboot).
- **06:46:04** — last journal entries: routine Docker health checks, all
  200 OK. Journal stops mid-stream.
- **06:46–06:50** — death window (the 06:50 sysstat collection never ran).
- **12:22:36** — manual power-on. ext4 orphan cleanup on nvme0n1p2; system

  18 containers healthy, HA API 200, all llama `/health` 200).

## Root cause chain

**1. The hang: hard platform lockup, same class as 6/8, 6/9, 7/18.**
No OOM, no MCE/EDAC, no thermal event, no amdgpu error, no panic. kdump was
armed (`crashkernel=` + kexec loaded) and produced **no dump**, and
`hardlockup_panic=0` — so the kernel never even reached its panic path.
Interrupts died with the journal mid-write. This is a firmware/SoC-level
wedge, not a software crash.

**2. The ROCm idle-spin is back — devstral is the spinner.**
The 6/9 fix moved the gemmas to Vulkan, but `llama-devstral-q4.service`
runs the **`llama-gfx1151-rocm7`** build. Today, with every server idle
("all slots are idle", zero requests, ~0 ns `drm-engine-gfx` in fdinfo —
the exact "unattributable busy" signature from 6/9), the iGPU sat at
**100 % busy, sclk pinned at 2900 MHz, ~48–62 W package**. Elimination
test (same method as 6/9): stop devstral → 0 % busy / 600 MHz / ~20 W
within seconds; start devstral → 100 % again.

**3. Why devstral escaped the June dragnet.**
Per `INCIDENT_2026-07-06_devstral_unit_down.md`, devstral was stopped
5/31 → 7/6 — it was **down during the 6/9 elimination tests** and absent
from that table. It returned 7/6, was later enabled, and has auto-started
(ROCm build, spinning 24/7) on every boot since 7/18.

**4. Why the outage lasted 5.6 hours: the watchdog has been dead since 7/18.**
The 6/9 safety net (sp5100_tco + `RuntimeWatchdogSec=2min`) **worked on
7/18** — boot -1's kernel log records `Previous system reset reason
[0x02000800]: hardware watchdog timer expired`, i.e. the 7/18 19:23 "reboot"
was actually silent hang #3, auto-recovered in ~60 s. But the module had
only ever been loaded **manually** on 6/9. Boot-time loading via
`/etc/modules-load.d/sp5100_tco.conf` never worked: Ubuntu's per-kernel
`/lib/modprobe.d/blacklist_linux_6.17.0-*.conf` (line 62) blacklists
`sp5100_tco`, and systemd-modules-load honors the kmod deny-list —
every boot since 7/18 logs `Module 'sp5100_tco' is deny-listed (by kmod)`.
No `/dev/watchdog` existed today, so `RuntimeWatchdogSec=2min` armed
nothing, and the box sat frozen until manually power-cycled.

## Hang ledger (updates the 6/9 table)

| Span | ROCm spinner resident? | End | Recovery |
|---|---|---|---|
| 6/09 → 7/06 (27 d) | no (gemmas→Vulkan 6/9; devstral down) | — | clean window |
| 7/06 → 7/18 (12 d) | **yes** (devstral back 7/6) | hang 7/18 19:23 | watchdog reset, ~60 s |
| 7/18 → 8/12 (25 d) | **yes** (devstral enabled, every boot) | hang 8/12 ~06:46 | watchdog dead → manual, 5.6 h |

Correlation across all five genuine hangs: every one occurred with at least
one ROCm llama build resident and spinning; the single long clean-idle
window (6/9 → 7/6) is also the only spinner-free window. Still a theory,
not a conviction — the mechanism (constant SMU/firmware burn → eventual
wedge) remains unproven, and 12 d vs 25 d is not a clean dose-response.
But the correlation strengthened, and nothing else abnormal was found.

## Ruled out today (with evidence)

- **Memory/OOM** — sar flat at 47 % used, no swap motion, to the last sample.
- **Update activity** — apt found nothing at 06:06; fwupd metadata-only 06:12.
- **New kernel** — 6.17.0-41 never ran before the hang (first boot: today).
- **Thermal shutdown** — box stayed powered (frozen, not off).
- **mt7925 WiFi** (6/9 suspect list) — interface DOWN all boot; primary NIC
  is wired `enp191s0`.
- **Kernel panic** — kdump armed, no dump, `hardlockup_panic=0`.
- **Workload** — zero llama/whisper requests all morning; quiet system.

## Fixes / follow-ups (priority order)

1. ~~**Kill the spin again: move devstral to a Vulkan build**~~ — **done
   2026-08-12** (same day). `llama-devstral-q4.service` switched to
   `llama-b9611-vulkan` (repo + installed copies). Measured: prompt
   370→300 tok/s (−19 %), generation ~14.6 tok/s unchanged; idle back to
   0 % busy / 600 MHz / ~20 W package. Verified through LiteLLM
   (`devstral-2512-q4`, fingerprint b9611).
2. **Resurrect the watchdog so it survives reboots** — unit authored
   2026-08-12 (`systemd/sp5100-tco-load.service`), **pending root install**
   (ops recipe in the unit's header). `modules-load.d` cannot win against
   the kmod deny-list; the unit does an explicit `modprobe` (which ignores
   the blacklist) then `daemon-reload` to re-arm PID 1. Success criterion,
   checked after a reboot: journal shows
   `Using hardware watchdog 'SP5100 TCO timer' ... /dev/watchdog0`.
3. **BIOS update** — still 03.03 (2025-09-16); this was 6/9 action item #2
   and remains open. Framework has shipped Strix Halo firmware fixes since.
   Operator will schedule.
4. ~~**Automate the GPU-idle canary.**~~ — **done 2026-08-12** (same day).
   New alert class in `scripts/memwatch.sh`: fires when `gpu_busy_percent`
   ≥ 95 for 5 consecutive polls (5 min) while the model fleet accumulates
   < 1 % of the interval in `drm-engine-*` time (real Vulkan inference
   measures ~95 % of wall on `drm-engine-compute`; the wedge measures ~0 —
   verified against live idle and live inference). ROCm/KFD work is
   invisible to fdinfo, so a reintroduced ROCm build trips the alert even
   while working — deliberate. Test recipe (`MEMWATCH_DRY_RUN=1`) in the
   script header.
5. Consider `kernel.hardlockup_panic=1` so a detectable lockup panics into
   kdump and leaves a vmcore (best-effort — today's wedge may be below the
   NMI watchdog's reach; the hardware watchdog is the real net).

## What would have caught it sooner

- **A post-reboot watchdog check.** The watchdog silently died at the 7/18
  reboot; nothing verified `/dev/watchdog0` after any boot. Belongs in the
  planned `check_all.sh` (ROADMAP items 8/9) alongside the LiteLLM health
  sweep from the 7/06 incident.
- **The GPU-idle canary from the 6/9 doc, automated.** It was written down
  as a manual command ("expect ~0 idle") and never run again.
