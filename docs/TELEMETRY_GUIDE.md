# Kronk Telemetry — Operator's Guide

How to use the Grafana + Tempo deployment (Telemetry v2, 2026-11-08). What
it is and how it is built: `features/telemetry.md`.

Grafana: **http://kronk:3000**. Dashboards are readable without a login;
editing needs the admin account in `.env.telemetry`.

---

## The #1 thing: seeing the stages of ONE request

**Explore → Tempo**, or any trace link from a dashboard.

1. Grafana → **Explore**, datasource **Tempo**. Query type **Search**:
   pick a span name (`pipeline.shim`, `voice.run`, `tool.play_music`…) or
   type TraceQL: `{ span.kronk.rid = "b43cadac" }`.
2. Click a trace → the **waterfall**: every stage as a nested bar, sized by
   duration, across services (orchestrator → tool_service in one view).
   Click a bar for its attributes: model, tokens, TTFT, tool, MA command,
   outcome, error text.
3. The rid in a spoken error ("… rid b43cadac") and the `rid` in the
   orchestrator's `kronk.events` log lines are the same `kronk.rid`; those
   log lines also carry the `trace_id` to paste into Explore's **TraceQL**
   tab for a trace-by-id lookup.

Timing: a trace is fetchable by id as soon as it is exported (about a
second) and shows up in **search and dashboards once Tempo cuts its
live-store block — 30 to 90 seconds**. Voice runs appear about two minutes
after the utterance (voice_tracer waits for the Kronk trace to be
searchable before linking to it).

## The dashboards (Kronk folder)

| Dashboard | Answers |
|---|---|
| **Overview** | Requests per hour by transport; end-to-end p50/p95 by transport; voice runs per hour and p50/p95 by who answered (blueprint / HA built-in / Kronk); errors; routes |
| **Stages** | p50/p95 over time per stage: STT (listen vs transcribe), intent, TTS, blueprint by trigger, routing, LLM rounds by model+phase, TTFT, tokens/s, agents, tools, tool internals (MA commands, HA service calls), outbound HTTP |
| **Slowest requests** | Tables of traces slower than `$min` (default 5 s): Kronk requests, voice runs, blueprint runs, the slow span inside a request, errored requests. Click a trace ID → waterfall |
| **Music** | `play_music` breakdown (resolve / pandora_station / genre_plan / play_verified), `play_media` inside HA+MA, verify-wait and resolver outcomes, Kronk path vs blueprint fast path, recent music traces |

Dashboards are **provisioned from `telemetry/grafana/dashboards/*.json`**
(generated by `telemetry/grafana/build_dashboards.py`). UI edits are not
saved — change the generator, run it, Grafana reloads within 30 s.

## Span names

Orchestrator (`resource.service.name = "kronk-orchestrator"`):

| Span | What it is | Key attributes |
|---|---|---|
| `POST /message`, `POST /api/chat`, `POST /voice/api/chat`, `POST /v1/chat/completions` | The HTTP request (auto) | `http.route`, `http.status_code` |
| `pipeline.message` / `pipeline.shim` | One pipeline run, request in → last token | `kronk.rid`, `kronk.transport` (webui / openai / ollama / voice), `kronk.route`, `kronk.origin.device_id`, `kronk.origin.area`, `kronk.error` |
| `routing.decide` | Shortcut router | `kronk.rule` |
| `agent.<name>` | A specialist's (or the coordinator's) whole tool loop | `kronk.agent`, `kronk.model` |
| `llm.<model>` | One LLM round | `kronk.round`, `kronk.phase` (`plan_N` / `synthesis` / `synthesis_forced`), `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `kronk.ttft_ms`, `kronk.tokens_per_sec`, `kronk.tool_calls`; event `first_token` |
| `tool.<name>` | One tool call (including `ask_<agent>` delegations, whose `agent.<name>` nests inside) | `kronk.tool`, `kronk.args_keys`, `kronk.output_chars` |
| `GET` / `POST` (client) | httpx calls: LiteLLM, tool_service, health/finance services (auto) | `http.url`, `http.status_code` |

tool_service (`kronk-tool-service`):

| Span | What it is | Key attributes |
|---|---|---|
| `POST /music`, `GET /search`, … | The incoming request, child of the orchestrator's tool span (auto) | `http.route` |
| `music.resolve` | MA search + scoring for a named request | `music.media_type`, `music.stage`, `music.candidates`, `music.best_score`, `music.outcome` (winner / below_threshold / nothing) |
| `music.pandora_station` | MA name lookup for a radio request | `outcome` (owned / created / not_pandora / no_item / ma_error) |
| `music.genre_plan` | Taste-based picks for a genre request | `music.forced`, `music.picks`, `music.outcome` |
| `music.play_verified` | HA `play_media` + the wait for the player to change | `music.outcome` (started / started_after_failure / failed / resolve_miss / no_start), `music.failure` |
| `ma.command` | One Music Assistant websocket command | `ma.command` |
| `ha.call_service` | One HA service call over the websocket | `ha.domain`, `ha.service`, `ha.entity_id` |
| `ssh.exec` | MagicMirror / ops SSH subprocess | `ssh.program`, `ssh.target`, `ssh.exit_code` |
| `GET` / `POST` (client) | HA REST, NWS, SearXNG, fetched pages (auto) | `http.url`, `http.status_code` |

voice_tracer (`kronk-voice-tracer`), from Home Assistant's own records:

| Span | What it is | Key attributes |
|---|---|---|
| `voice.run` | One Assist pipeline run, HA's first event → run end | `ha.pipeline_run_id`, `ha.satellite_id`, `kronk.origin.device_id`, `voice.handled_by` (blueprint / ha_local / kronk / blueprint_then_kronk), `voice.response_type`, `voice.transcript_chars`, `voice.wake_detection` (always `satellite`: the wake word is detected on the device, HA never sees it), `kronk.trace_id` + span link when Kronk answered, `ha.blueprint_trace_id` + link when the blueprint ran |
| `voice.stt` → `voice.stt.listen`, `voice.stt.transcribe` | Stream start → VAD end (speech + trailing silence), then Whisper | `voice.engine`, `voice.vad_start_ms`, `voice.vad_end_ms` |
| `voice.intent` | Intent stage: sentence trigger / built-in intent / Kronk | `voice.processed_locally`, `voice.engine`, `kronk.trace_id` |
| `voice.tts` | The TTS request (HA streams synthesis, so this is near zero) | `voice.engine`, `voice.voice` |
| `blueprint.run` | One run of the music blueprint automation | `bp.trigger_id`, `bp.outcome` (played / handed_to_kronk / failed / finished), `bp.target`, `bp.media_type`, `ha.pipeline_run_id` + link |
| `ha.music_assistant.play_media`, `ha.media_player.shuffle_set`, `bp.wait`, `bp.handoff_kronk` | Blueprint steps, timed from HA's trace | `bp.path`, `bp.alias` |

No prompt, answer or transcript text is on any span unless
`TELEMETRY_RECORD_TEXT=true` on the containers; `kronk.events` keeps its
80-char previews either way.

## TraceQL cheat sheet

```
{ span.kronk.rid = "b43cadac" }                         # one request by rid
{ name = "pipeline.shim" && duration > 10s }           # slow voice/shim runs
{ name = "voice.run" && span.voice.handled_by = "kronk" }
{ name = "ha.call_service" && span.ha.service = "play_media" && duration > 5s }
{ name =~ "pipeline\\..*" && status = error }
{ name = "music.play_verified" && span.music.outcome != "started" }

# metrics (Explore → TraceQL, or a dashboard panel)
{ name =~ "pipeline\\..*" } | quantile_over_time(duration, .5, .95) by (span.kronk.transport)
{ name =~ "llm\\..*" } | quantile_over_time(span.kronk.ttft_ms, .5, .95) by (span.gen_ai.request.model)
{ name = "blueprint.run" } | count_over_time() by (span.bp.trigger_id, span.bp.outcome)
```

## Escape hatch: Tempo's HTTP API

Tempo listens on `127.0.0.1:3200` on the host (and `tempo:3200` on the
docker network — that is what voice_tracer uses).

```bash
curl -s localhost:3200/ready
curl -s -G localhost:3200/api/search --data-urlencode 'q={ span.kronk.rid = "b43cadac" }'
curl -s localhost:3200/api/v2/traces/<trace id>            # the full trace as JSON
curl -s -G localhost:3200/api/metrics/query_range \
  --data-urlencode 'q={ name = "voice.run" } | quantile_over_time(duration, .5, .95)' \
  --data-urlencode since=24h --data-urlencode step=1h
```

## Operational notes

- Stack: `docker-compose.telemetry.yml` (ops recipes in its header). Never
  `down -v` — `tempo-data` is every trace, `grafana-data` the login.
- Retention: 90 days (`block_retention: 2160h` in `telemetry/tempo.yaml`).
  Size it with `docker system df -v | grep kronk-telemetry`.
- Off switch: `TELEMETRY_ENABLED=false` in the environment when running
  `docker compose up -d orchestrator tool_service voice_tracer` turns every
  span into a no-op (`.env` or the shell). voice_tracer keeps reading HA but
  exports nothing.
- Tempo down → each service logs a failed export batch and drops it; no
  request is slowed (export is a background thread). voice_tracer retries its
  HA connection with backoff and never crashes on an export failure.
- Grafana phones home nowhere: usage stats, update checks, plugin catalog,
  gravatar and the news feed are off in the compose environment.
- `tool_service`'s `/health` and the orchestrator's page loads, probes and
  Ollama discovery calls are excluded from server spans; a background poll
  (weather cache, solar) that makes an outbound call outside a request is
  dropped by the sampler rather than becoming a one-span trace.
- Never send Tempo a span older than `ingestion_time_range_slack` (15 min,
  `telemetry/tempo.yaml`). Beyond it the span is not only unfindable by
  ranged search — Tempo 3.1.1 wrote blocks with inverted time bounds and
  every metrics query overlapping them returned 500 `end must be greater
  than start` (2026-11-08; fixed by deleting the blocks). voice_tracer
  therefore backfills only the last 10 minutes at startup; older HA runs are
  still in HA's debug list but are not traced. If dashboards ever go blank
  with that error, list `meta.json` files under the `tempo-data` volume for
  `startTime > endTime` and remove those block directories with Tempo
  stopped.
