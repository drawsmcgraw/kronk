Severity: blocker, should fix, note. Paths were under

### Should fix

**1. A production tag that is not a local ref: `OK`, and the notice says
nothing.** Reproduce: scratch house, HEAD pushed, the canned `docker ps`
says production runs from `kronk-releases/sprint-NOPE`, no tag of that name
in the repo; run the config backup. Result: exit 0, `config backup OK`, the
notice is only the file name, size and totals. `repo-state.txt` says
`unpushed bundle: none needed: every commit of HEAD is on a remote-tracking
branch; left out, not a local tag: sprint-NOPE` and `production tag
sprint-NOPE on the remote: unknown (no local tag of that name)`, with no
commit id, so the runbook's `git tag <tag> <commit>` line has nothing to
offer. The same beside an unpushed tag that is a local ref: the notice
names that one and is silent about `sprint-NOPE`. The "left out" clause
reaches the notice only when git's count fails. Reach: a deployed tag
deleted from the local repo. Whether the remote has it cannot be told
without contacting it. Fix: when `missing` is not empty, add to the notice
`Production tag X is not a local tag: the tar cannot say which commit
production runs`; a test. The feature doc's "left out of the bundle and
named" should say where it is named.

**2. Unpushed commits on a local branch other than the checked-out one are
neither in the bundle nor in the notice.** Reproduce: HEAD on `main`
(pushed), production tag pushed, branch `wip` with two commits no remote
has; run the config backup. Result: `OK`, no bundle, the notice says nothing
about the repo, `repo-state.txt` says `on no remote-tracking branch (HEAD
and the production tags): 0 commit(s)`. The same for a stash. This is the
scope the feature doc states ("HEAD, the branch and the production tag"),
and a restore of the running system does not need it. But a notice with no
repo sentence reads as "everything is pushed", and the working tree parked
on `main` on the night of the 10th while `refactor` holds a sprint's
unpushed work is the reach the third report gave for its finding 1. Today
the tree is on `refactor`, so today's tar holds all 22 unpushed commits.
Fix: count `git rev-list --count --branches HEAD <tags> --not --remotes`
and bundle `--branches`, or at least one notice sentence, `N commits on
other local branches (wip, ...) are on no remote and not in the tar`. The
feature doc's "only the unpushed commits are in the bundle" should name the
scope.

**3. The runbook's step 5 fails as written in three repo layouts the code
handles.** Each run in a clone of the stand-in remote, with the tar's own
bundle.
- Bundle holding only tags (HEAD pushed, production tag unpushed: the
  layout round 3 fixed). `git fetch ... '+refs/heads/*:refs/remotes/bundle/*'
  '+refs/tags/*:refs/tags/*'` brings the tag; the next line, `git checkout
  -B <branch> bundle/<branch>`, ends `fatal: 'bundle/main' is not a commit
  and a branch 'main' cannot be created from it`. Harmless, but it is an
  error in the middle of a restore.
- Local-only branch. The first command, `git checkout <branch from
  repo-state.txt>`, ends `error: pathspec 'sprint-local' did not match any
  file(s) known to git`; the bundle block that follows then works.
- Detached HEAD on unpushed commits. `repo-state.txt` says `branch: HEAD`
  and the bundle's only ref is `HEAD`. The runbook's refspecs match no ref,
  so the fetch brings nothing, `git checkout -B HEAD bundle/HEAD` fails, and
  the commit named in `commit:` is not in the clone (`git cat-file -e`
  fails) while the notice said "the tar holds them as
  repo-unpushed.bundle". They are in the tar: `git fetch
  $R/repo-unpushed.bundle HEAD && git checkout FETCH_HEAD` gets them.
Fix: in step 5, run `git bundle list-heads` first and say what to do for
each of the three (skip the first checkout when the branch is not on the
remote; skip `checkout -B` when the bundle has no `refs/heads/<branch>`;
fetch `HEAD` when that is its only ref). With a branch that has a remote
counterpart (today's layout) the step works as written.

**4. Retention removes the tar the run just wrote when twelve newer dates
are already there.** Reproduce: twelve tars named `kronk-config-2027-01-10`
to `2027-12-10` in `config/`, run the config backup. Result: exit 0, `OK`,
and the notice ends `Removed by retention: kronk-config-2026-11-19.tar.gz`:
its own file. `status.json` records `ok` with a `last_ok_path` that does
not exist. Reach: the clock set back (a dead RTC with no time sync at
01:30), or tars with wrong dates in their names. The newer tars stay, and
the notice does name the file, so nothing is hidden; but a run that deletes
its own result should not say OK. Fix: never remove the name just written
(or fail the run when it would), and a test.

### Notes

5. **The delete script's last look at the local file is before it reads
   the destination copy, not right before the `rm`.** The script hashes
   the local file, takes its size, mtime and inode, then hashes the
   destination copy and takes that copy's inode, then compares and removes.
   A file put under the recording's name by rename while the destination
   copy is being read is removed without ever having been copied, and the
   run says OK. Shown with the direct delete and a `sha256sum` shim on
   `PATH` that swaps the file during the second hash: exit 0, the
   replacement neither local nor on the destination. The window is the read
   of one copy from the share (milliseconds for a 150 KB recording) and it
   needs another process to replace a recording more than seven days old;
   Home Assistant does not rewrite old recordings. Every check before that
   window held in every swap I placed. Fix: read the destination copy
   first, the local file's hash and stat last, so the window is the one
   shell line the feature doc already claims ("the one shell line between
   the last read and the `rm`"; today that sentence is true of the
   destination copy only).
6. **Mutants no test notices** (list below): another user's pid counted
   as dead in the orphan cleanup; the stale check not comparing the status
   path's directory with the destination; the probe unlinked without its
   inode check; a dry run going on to print a move for an undatable file;
   HA's tar retried on any failure, not only exit 1; and the third
   report's cv7, which round 3 did not pin. The real code behaved correctly
   where I exercised these by hand (a decoy named for pid 1 was kept; a
   status path on another destination fell back to the tar's name).
7. **A corrupt status file is set aside, and nothing says so.**
   `status.json.unreadable-<epoch>` appears beside the new file, but the
   "set aside" note `read_status` returns is dropped: the reader that moves
   the file is not the one that writes. The check then warns "the
   recordings archive has never finished a run", which is loud enough.
8. **A declined archive logs no reason.** The config job logs `declined:
   another backup job holds the lock (...)`; the archive only logs `notice
   not sent`. The reason is in the status file and the notice.
9. **A recording dated in the future is never archived and never
   mentioned** (2031, and a year past 9999): it is counted in "remain
   local" only. One dated before year 1 is reported each run, as built.
10. **A hung notifier's child outlives the 60 s timeout.** The timeout
    kills the command it started; a `sleep` that command had started was
    still there afterwards. Under systemd the unit's cgroup would take it.
11. **When git cannot read the repo at all** the notice says `Working
    tree: 1 uncommitted or untracked path`: the one line counted is git's
    error. The same notice does say the unpushed count is unknown.
12. **HA's tar exiting 2** (or any code but 1) is not read again; it is
    INCOMPLETE at once. As documented.
13. **Scheduling, read in both codes.** `upgrades.py` and `deploy_tag.sh`
    never look at the backup lock. A backup job takes its own lock, then
    tests the upgrade lock with a shared non-blocking `flock` it releases
    at once, once at its start and once a minute while it waits. No cycle,
    so no deadlock. An upgrade run or a `deploy_tag.sh deploy` that tries
    the lock in that instant would see it held and decline once; the
    upgrade timer fires again the next night of its window. An archive
    still running at 03:30 on a Monday of days 1 to 7 would run beside the
    upgrade (ruling 10: documented, not built). The services have no
    ordering on Docker or the share; the bounded wait covers the share.
14. **Still open until the first real mount**, as the third report said:
    `/tmp` is tmpfs and the home filesystem ext4, both with hard links and
    `renameat2`. Which placement the Synology takes, and a read-back that
    really comes from the server, are for the watched first run.
15. **Tester's notes.** (a) This host's `truncate` is uutils and rejects
    `-s -1`: one of my hooks did not fire in three runs; redone with an
    absolute size, three passes. (b) My harness flagged nine runs that
    behaved correctly: six where my own hook had renamed `recordings/`
    away, so my canary's path moved with it (both recordings kept, the
    directory not recreated, Docker refused the bind mount), and three
    two-at-once runs where I had expected a log line the archive does not
    print (note 8). (c) My secret search matched one value twice, in two of
    my own harness logs: a 12-character account name that is the same
    string as a fixed name in the code. Not a leak. (d) The suite run left
    one more `/tmp/kronk-m9-bytes-*` directory (503 now, 502 before); not
    removed, as instructed.
