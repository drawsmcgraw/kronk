## Finding

### T1. A command that had to be killed is reported as "could not reach the host" (criterion 12; error accuracy, not a bypass)

The fix maps remote exit 124 and 137 to a 504 that names the cause. Exit 137
never arrives through a real `ssh`. GNU `timeout -k` sends KILL to its own
process group, which includes itself; the remote command therefore dies of a
signal, `sshd` reports a signal rather than an exit status, and the `ssh`
client exits 255 with nothing on stderr. `ops_exec` reads 255 as a transport
failure.

Shown in the sandbox through a real `sshd` (OpenSSH 10.0p2, coreutils 9.7),
with the shipped limits and a process that ignores TERM (built by hand; the
classifier refuses the line, this tests the wrapper only):

```
F. TERM-ignoring process through sshd, shipped limits. sent: timeout -k 2 25 bash -c 'trap '"'"''"'"' TERM; while :; do read -t 1 x </home/pi/fifo; done'
   ssh rc=255 elapsed=27.1s stdout='' stderr=''
   survivors: []
   in REMOTE_TIMEOUT_EXIT_CODES: False
```

And what the route does with that result (scratch copy, stub in place of
`ssh` returning `(255, "")`):

```
stub rc=255: 'cat /home/pi/fifo' @sbx -> 502 {"detail": "could not reach sbx: connection failed"}
```

The process is gone, so the safety property holds. The user is told the
host was unreachable when it was reached and the command was killed there,
and the audit line records `exit_code: 255`. The unit test
`test_remote_timeout_kills_a_process_that_ignores_term` accepts `-9` as
well as 137, which is the same effect seen without `ssh` in between; the
route test feeds 137 by hand. For the fix agent: tell the two 255 cases
apart (a transport failure has text on stderr and returns before the remote
limit; a kill returns at about 27 s with none), or have the wrapper report
the kill itself, for example by running `timeout` under a shell that prints
a marker when the child exits by signal. Whether an allowed read-only
command can ignore TERM at all is a question for the fresh sweep.

### The two grep --color rows

The fixer's claim: `grep -r --color never BEGIN` is not a bypass, because
`--color` takes a value only as `--color=WHEN`; grep reads `never` as the
pattern and `BEGIN` as the file, and so does the classifier. Checked:

```
'grep -r --color never BEGIN' (True, 'read-only')
'grep -r --colour never BEGIN' (True, 'read-only')
'grep -r --color=never BEGIN' (False, 'grep: recursive search with no directory searches the home directory; name a directory')
'grep -r --color never' (False, 'grep: recursive search with no directory searches the home directory; name a directory')

$ grep -r --color never BEGIN            # sandbox, fake home, GNU grep 3.11
grep: BEGIN: No such file or directory
exit 2
$ mkdir BEGIN; echo "never here" > BEGIN/f; grep -r --color never BEGIN
BEGIN/f:never here
exit 0
```

grep searched `BEGIN` for `never` and did not search the home. The claim is
correct. `~/BEGIN` as a root is a relative directory three components deep,
which is the floor the ruling accepts for `grep -r`.
