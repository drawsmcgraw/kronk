## Observations

1. **`http_check` failures are not recognised as failed results.**
   `[http_check http://127.0.0.1:9: FAILED (connect) after 12 ms: …]` does
   not match `_FAILED_RESULT`, so on the speech mount the model gets no
   phrasing rule and the turn is not marked failed. With a stub that echoes
   the result, `/voice/api/chat` spoke
   `NO-RULE [http_check http://127.0.0.1:9: FAILED (connect) after 12 ms: ConnectError: [Errno 111] Connection refused].`
   (P22). Live the model wrote
   `http://127.0.0.1:9 is not reachable. The connection was refused.`,
   which repeats the URL the user asked about.
2. **The backstop's shapes are the code's own, so other technical text
   passes.** A stub model saying "The weather lookup failed with HTTP 500
   because api.weather.gov returned 503 to tool_service." on a failed turn
   is spoken as written (P24). `debug_shape` finds nothing in "HTTP 503 from
   api.weather.gov", "tool_service-dev returned 502", "gemma-4-e4b via
   LiteLLM said no", `{"detail": "x"}`, "10.0.0.5 did not answer on port
   8080", "http://10.0.0.5/x" or "[rid abcd1234]". Model-written failures
   stay instructed, not guaranteed, for those. Live: 0 of 48.
3. **Model-written sentences, live (section 5).** 48 voice requests had a
   failed tool; 47 were spoken as the model wrote them and one was replaced
   by the backstop (finding 2). None of the 47 contains an exception name,
