pre-M11 code does, with shadow off and with shadow on; the shadow cannot play

them: "play the album Jazz" (a criteria example) is read correctly as a named
album but lands on a Depeche Mode track on dev (finding C1), and criterion 14

## Findings for the cutover review

**C1. The cross-type retry accepts a partial-name match.** `play the album
Jazz` on dev: read as a named album (the type word overrides the genre list,
which is what criterion 5 asks), no album scores above 0.59, and step 4 then
takes the library track "Jazz thieves" by Depeche Mode at 0.95 and would play
it. The builder added `title_min_score` so that a part-of-a-name match does not
decide an unmarked request ("play italian"); the same match still decides a
typed one through `cross_type`. Same shape: `play the song Spotify by Yeat`
plays the album "Spotify" by Performance (3.9 s). I did not count this as a
failed criterion because the criterion's example is about the reading, and the
reading is right; what plays is wrong.

## Shadow on and off (criterion 15)

Dev, `POST /music` on 127.0.0.1:8103, dry run on, the same 40 corpus requests
per pass; shadow off by a scratch compose override for `tool_service-dev`

| Pass | Shadow on: p50 / p95 / max | Shadow off: p50 / p95 / max |
|---|---|---|
| Spaced 2 s apart | 22 / 71 / 75, 21 / 70 / 71 | 20 / 68 / 74 |
| Back to back | 29 / 78 / 93, 24 / 59 / 75, 24 / 70 / 74, 23 / 73 / 88 | 14 / 52 / 67, 13 / 55 / 69 |

- Answers: 480 pairs against the shadow-off spaced pass; 445 identical; the 35
  that differ are the five style rows, whose pick is a weighted random choice
  among the top three and varies between shadow-off passes too.
- The builder's back-to-back numbers are real: about 10 ms at p50 and 5 to 25
  ms at p95, because the previous request's shadow is still deciding on the
  same event loop. Spaced 2 s apart there is no difference. For a household,
  where requests are seconds or minutes apart and a real play takes seconds
  (`play_media` and a verify poll of at least 1 s), it is not observable.
- A slow or hung Music Assistant read in the shadow does not delay the next
  live request (offline stub): with every shadow read hanging 0.5 s, 30 live
  requests back to back took p50 0.6 ms, max 17 ms, against 1.3 and 27 ms with
  no hang; with reads hanging 5 s and a 0.3 s shadow timeout, p50 1.0, max 24
  ms, and 24 records say "timed out". Each Music Assistant command opens its
  own websocket and there is no shared lock. Shadows run one at a time, so a
  hung Music Assistant builds a queue of waiting shadow tasks (30 s each at
  the default timeout); they hold only the request and its answer.
- Faults (offline): the live answer equals the shadow-off answer in all 16.

| log directory or file not writable, path is a directory, parent is a file, disk full | no | warning "could not write" |
| data directory missing | yes (created) | info |
| live request fails (unknown speaker), with and without a shadow failure | yes | info / warning |

  worker), so lines cannot interleave.
