## Findings

Severity: blocker, should fix, note. Paths were under `/tmp/kronk-m16-e2e3`
(removed). Archive cases ran the real `scripts/backups.py` with the real
`alpine:3.20` delete on root-owned trees. Config cases other than the one
real run used a scratch house: a scratch git repository with its own user
and a bare stand-in remote, a scratch `HOME` and live config, fake secret
values, and a canned `docker` on `PATH` that answers for the HA, MA and
helper reads.

### Blocker

**1. An unpushed production tag is left out, silently, when HEAD is
pushed.** Blocker by the brief's definition; narrow.
Reproduce: scratch repository whose remote has commits c1 and c2; c3 and c4
exist only locally, tag `sprint-T1` on c3; production (the canned `docker
ps`) runs from `kronk-releases/sprint-T1`. Check out a pushed commit in the
working tree (`git checkout -b side sprint-T0`, or `main` when it is
pushed), run the config backup. Result: exit 0, `Kronk backup: config backup
OK`, no `repo-unpushed.bundle` in the tar, and the notice is only the file
name, size and totals. `repo-state.txt` says `unpushed bundle: none needed:
every commit of HEAD is on a remote-tracking branch` and, further down,
`production tag sprint-T1 on the remote: no: its commit … is on no
remote-tracking branch (the tag is in repo-unpushed.bundle when that member
exists)`. That member does not exist. The code production runs is on this
disk only.
Cause: `unpushed_bundle` returns early on `git rev-list --count HEAD --not
--remotes` being 0; the tags are only looked at after that.
Reach: the working tree parked on `main` or any pushed commit on the night
of the 10th while a deployed tag has not been pushed. Releases run from
`kronk-releases/<tag>`, so the working tree's branch is free to be anything.
Today HEAD is ahead of both production tags and both tags' commits are on
`origin/refactor`, so today's tar is whole.
Why not lower: the feature doc says the bundle holds "HEAD, the branch and
the production tag less everything a remote-tracking branch has"; the
runbook's step 11 deploys the production tag, which a restore from this tar
cannot have; the notice, the status result and `/services` all say OK.
Why it could be lower: the tar does say the tag's commit is on no remote;
the criteria do not require a bundle; no household data is involved.
Fix: count over HEAD and the verified tags (`git rev-list --count HEAD
<tags> --not --remotes`); put "production tag X is not on the remote" in the
notice whenever `tag_on_remote` answers "no", bundle or not; a test with
HEAD pushed and the tag unpushed.

### Should fix

**2. On a branch with no remote counterpart the notice never mentions
unpushed commits, nor an omitted or failed bundle.** The notice's sentence
comes from `not pushed: N commits ahead of <upstream or origin/<branch>>`.
On a local-only branch that `rev-list` fails, `repo-state.txt` reads `not
pushed: unknown, (git rev-list --count origin/sprint-local..HEAD failed: …)`,
and the notice says nothing about the repo. Reproduced: (a) local-only
branch, 2 unpushed commits: the bundle is in the tar, the notice silent;
(b) the same with a 2.5 MB commit and `KRONK_BACKUP_BUNDLE_MAX_MB=1`: `OK`,
no bundle, `repo-state.txt` says `OMITTED: 3 commit(s) unpushed … push
them`, and the notice says nothing. The feature doc ("left out over 20 MB …
and the notice says so") and the runbook's step 5 ("it is left out, and the
notice says so") are not true there. Fix: take the notice's count from the
same `--not --remotes` count the bundle uses, and always carry an `OMITTED`
or `NOT WRITTEN` note into the notice.

**3. `status.json` is read, changed and written back with no lock, and the
check does it across its wait for the mount.** Reproduced: a `check` with
`--require-mount` on a directory that is not a mount, wait 20 s; an archive
run with the same state directory finished meanwhile and wrote `archive:
ok`; when the check ended it wrote back the copy it had read at its start,
and the archive's entry was gone ("the recordings archive has never
finished a run"). The realistic form is the `Persistent` catch-up at boot,
when all three timers fire together and wait for the share. A declined job
also writes the file while the other job holds the lock. Nothing is lost
but the record: `/services` and the stale check then show an older run, or
hide a failed one. Fix: re-read the file right before writing in
`cmd_check` (or take the backup lock for the write), and a test.

**4. Mutants that no test notices** (list below): the backup lock taken
shared instead of exclusive (two jobs would then run together: the tests
hold the lock themselves and never call `take_lock` twice); the leftover
cleanup following a symlink named like a bundle directory; a dry run and
the daily check creating and removing the write probe on the destination;
the temporary tar created 0644 and `config/` made 0755; a final tar name
that appears during the run being overwritten; "does not fit" keeping the
largest failed size; a failed notice recorded as sent; a replaced temporary
file not noticed before the read-back; a file at the wrong depth taken as a
recording (safe only because the run then aborts). The real code behaved
correctly wherever I exercised these paths by hand (the cleanup, the dry
run, the full destination, a failing notifier, a replaced temporary file,
wrong-depth files, two jobs at once); the temporary tar's mode and the
overwritten final name I did not exercise. The tests would not catch a
regression in any of them.

**5. A FIFO where a SQLite file is expected hangs the config job.**
Reproduce: replace `data/music_taste.db` with a FIFO in the scratch house.
`read_sqlite` opens it and blocks; my harness killed the run at 300 s. In
service the job would hold the backup lock until the unit's 3 h timeout and
the archive would decline after 30 minutes. A FIFO as a plain file source
is handled ("not a regular file"); this path is not. Fix: `lstat` and
require a regular file before `sqlite3.connect`.

### Notes

6. **A recording whose mtime is outside Python's date range stops the whole
   archive.** `touch -d @-70000000000` on one root-owned file: every run
   ends `FAILED: ValueError: year -249 is out of range`, nothing moved, and
   `--dry-run` ends in a traceback. Nothing is lost. A file dated 1970 is
   fine (it goes to `1969-12/`).
7. **HA's `tar` exiting 1 with a whole stream makes the tar INCOMPLETE.**
   With the canned `docker` returning the full stream and exit 1 ("file
   changed as we read it"), the run is INCOMPLETE, exit 4. HA's image has
   busybox tar, and HA rewrites `.storage` files by temporary file and
   rename, so a save that lands during the copy can do this. Loud, kept,
   and the next run is whole; expect it once in a long while.
8. **A killed job's delete container keeps running.** In the timed kills
   the local count fell from 200 to 0 after the job was dead: `docker run`
   was killed, the container was not, and it finished its batch. Every
   delete it makes is still preceded by the script's checks, a second job
   started meanwhile lost nothing, and no container was left afterwards.
   The same would follow the 600 s timeout of a batch. The lock is free
   while that container works.
9. **The stale check goes by the tar's mtime, not its name.** A 2025-named
   tar touched today reads as current; a current-named tar with an old
   mtime (copied back with `cp -p`) reads as stale.
10. **Retention counts same-day tars one by one.** With `KEEP=3`, two runs
    today and one `.10` tar from 2025-12 were all that stayed. Twelve
    by-hand runs in a day would leave only that day's tars.
11. **The rename window is real where neither `link` nor `renameat2`
    exists.** A file created under the final name between the fallback's
    check and its rename (injected) was replaced. Documented as residual.
    With `renameat2` available the same injection is a conflict, both kept.
12. **Uncommitted and untracked work is not in the tar.** `repo-state.txt`
    says `working tree: 2 changed paths`; the notice does not mention it.
13. **A zero-byte `solar.db` is a valid empty database**: the run is OK.
    A corrupt or missing one is INCOMPLETE, as ruled.
14. **Doc wording.** (a) "Housekeeping on the NAS" calls each
    `.kronk-archive.*.tmp` "a partial copy of a recording that is still
    local": a kill between the link and the unlink leaves a second hard
    link of a finished, verified copy, and after the next run the recording
    is no longer local. Deleting the leftover is harmless either way.
    (b) "The jobs never delete anything on the share except retention's old
    config tars": they also remove their own stale `.kronk-config-*.tmp`,
    and, read in the code, not run, a file already named
    `.kronk-write-probe` in the destination root is unlinked by the
    writability probe. (c) Finding 2's two sentences.
15. **Runbook, small points.** (a) Step 4's `sudo install … $R/etc/kronk/*
    /etc/kronk/` will overwrite the `nas-backup.cred` typed in step 2 with
    the tar's copy once the tar holds one; the same content unless the
    password changed since the tar. (b) Step 8 does not say to create
    `/opt/models` (root-owned parent). (c) Step 10's copy brings back three
    snap `*.wants` links, which the start line's pattern rightly skips.
    (d) Not run by me, for want of root or network: steps 1, 2, 4, the
    GitHub clone and `pip install` of step 5 (a stand-in remote and the
    repo's own venv instead), 8, 9, 11, the MA start of step 13, and 15.
    Steps 3, 5 (bundle), 6, 7, 10 (copy and verify), 12, the settings copy
    of 13, 16 and all three "restore one thing" blocks worked as written
    with only the volume and project names changed. With the system
    `python3` the config check prints `INVALID`, as the runbook warns.
16. **`Persistent` catch-up at boot.** The services have no ordering on
    Docker or the share. The bounded wait covers the share; a job that
    starts before Docker or HA is up ends INCOMPLETE (config) or with
    failed deletes (archive), loudly, and is not retried until its next
    date. No deadlock with the upgrade run: `upgrades.py` and
    `deploy_tag.sh` never look at the backup lock; the backup probes the
    upgrade lock with a non-blocking shared lock it releases at once, while
    holding its own. An upgrade run that tries its lock in that instant
    would see it held and decline once.
17. **Still open until the first real mount.** `/tmp` here is tmpfs: hard
    links and `renameat2` both work, and "page cache dropped" proves
    nothing about a read-back from a server. Whether the Synology takes
    `link(2)` or a fallback, `fchmod` and `utime` on CIFS, inode stability,
    and reads in `/proc/fs/cifs/Stats` are for the watched first run the
    feature doc describes.
18. **API.** Non-numeric `limits` in the status file switch the age
    warning off rather than falling back to 35 and 9; a `last_ok_at` in the
    future gives no warning. The script writes both fields itself.
19. **Tester's notes.** (a) My suite run left one more
    `/tmp/kronk-m9-bytes-*` directory (500 now, 499 before); not removed,
    as instructed. (b) The default-destination runs used the real wrappers
    with no `--src`, so the archive's source was the real recordings
    directory: each stopped at the destination check (exit 2) before any
    scan, and the listing hash is unchanged. (c) Three flags in my own
    tables were harness artifacts, each checked by hand: a destination copy
    I had made mode 000 could not be hashed by my snapshot (a root read
    showed the original hash); hooks that themselves overwrote a source
    before the job had copied it; and a name test that matched its own file
    names. (d) Importing `orchestrator/backups_api.py` for the offline
