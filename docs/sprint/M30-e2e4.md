## Findings

### 1. Blocker: a run inserted late and not yet final

`reopen_joins()` skips an inserted row whose end is younger than
`FINAL_S`. `audio_joins()` then waits for that row, but only for rows not
yet tried; a neighbour joined in an earlier run is not looked at again.

**Inside the premises** (Tempo has both runs on time):
`test_job1_a_catch_up_read_cut_at_a_day_mark_before_a_long_run_that_is_not_final_yet`
(xfail). The exporter was stopped for about a day. Its catch-up read goes
a day per search from the watermark less an hour; the budget ends at the
day mark. A ends 2 s before the mark, B starts 1 s after it and runs
120 s; one recording fits both. The cut run takes A (ended 952 s ago,
final) and joins it alone: `certain`. The next run, 60 s later, takes B
(ended 889 s ago, not final): `audio_reopened` absent. When B is final it
is stored `ambiguous`. A keeps `certain` for good. The join over both:
`ambiguous, ambiguous`.

**Outside voice_tracer's premise**, the same through Tempo:
`test_job1_a_long_run_tempo_shows_late_but_before_it_is_final` (xfail). B
is 300 s long and Tempo shows it 943 s after it started. This one rests on
Tempo being late, which the ruling named as a path; it is listed for
completeness, not as the blocker.

The hourly check's take cannot do it: a run the check takes started more
than an hour before the watermark, and no run the tracer exports is that
long.

Cure, for the coordinator: drop `r["end_s"] < now - FINAL_S` from
`reopen_joins()`. A set with a young row then waits whole, as it already
does for rows never tried. Cost: one closure per inserted row, which the
ordinary run already pays in `audio_joins()`.

### 2. Note: the re-open makes a large first read quadratic

`reopen_joins()` computes a closure for every inserted final row, and each
closure scans the rows older than it. A first read (`--init`, or a
rebuild from Tempo) inserts every row final:

| Rows inserted in one run | As built | Re-open off |
| :-- | :-- | :-- |
| 4,000 | 2.01 s | 0.33 s |
| 20,000 | 50.98 s | 1.73 s |

Inside one `BEGIN IMMEDIATE`. Tempo holds 90 days (113 runs today), so a
first read is hundreds of rows, not thousands; an ordinary run inserts one
or two. No action needed now. The fix, if ever: skip the re-open when the
set holds no tried row, or bound the closure's query below as well as
above.

### 3. Notes

- A removed row keeps the join it had. After a re-open its neighbour can
  be stored `certain` on the same recording the removed row still names.
  Rule 8 (never written again); the randomized test compares rows not
  removed.
- `http_get_json` restores the previous handler with
  `signal.signal(SIGALRM, old)`. If a handler had been installed from C,
  `old` is `None` and the restore raises `TypeError`. Not reachable in the
  CLI (the handler is `SIG_DFL`).

**Can the alarm fire outside the request?** No.

- `test_job3_no_timer_is_set_when_sqlite_or_a_file_is_written_even_after_requests_were_cut`:
  a whole export through the real `http_get_json` (urlopen faked), four

- `test_job3_a_request_that_ends_at_the_very_moment_of_the_bound_leaves_nothing_behind`:

  gone every time; no stray alarm.
- An alarm that lands after the answer was read and before the timer is
  cancelled turns a good answer into a failed read. Harmless: the read is
  made again next run.
- `TimeoutError` is an `OSError`, and the standard library catches those
  in places. Read: `socket.create_connection` re-raises it, `SocketIO`
  re-raises it, `urllib` wraps it in `URLError`. All end as `TempoError`.
  The five server cases above agree.
