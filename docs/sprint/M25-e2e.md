## Does the page do what Drew asked?

His words: "It should represent real usage information", and for scope:
"No hand-written number: context, quantization and model file read from
each running server; GPU busy, memory, disk used by models; per server,
requests and tokens in the last 24 hours and when it was last used."

In my judgment, yes. Every figure I could find on the page traces to a
kernel counter, a server's own answer, a `stat`, or a row count, and I
could reproduce each one from the host. Context, model file (the
quantization is in its name) and draft file come from the running
process. Memory is per process, GPU and RAM. Disk used by models is the
30.5 GiB of loaded files, which today is every model file on the disk.
Requests, tokens and last used are there per model. When a source goes
old the figures go away and the page says why.

What is still missing from "real usage information":

- **Activity is what this orchestrator recorded, not what the server
  did.** Not counted: the other instance's calls (dev made 166 calls in
  the window, production 47, on the same three servers); tool_service's
  music question, which goes to LiteLLM directly
  (`tool_service/main.py`, `MUSIC_MODEL_URL`); LiteLLM's health rounds;
  anything sent to a server by hand. The page says "calls from this Kronk
  only". The server's own counters would be the per-server truth, and
  they are off: `GET /metrics` on gemma answers 501.
- **GPU busy is one instant**, and on this box it reads 0 nearly always.
  It tells Drew little. History is in Grafana by his choice.
- **Nothing about now**: which slots are busy, how much context each
  holds. The servers answer `GET /slots` (200 on gemma).
- **Whisper has memory and no usage** (transcriptions in the window).
- **Disk counts loaded files only.** A model file kept on disk and not
  loaded would not appear. None exists today.
- **No timing** (tokens a second, time to first token): out of scope by
  the criteria.
- S2 and S3 above: two places where what is shown can mislead.
