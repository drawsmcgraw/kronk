## Why it fails

All seven criteria are met. The verdict is FAILS on two findings the test
brief grades as blockers. Both are small and neither was seen in normal
use; the coordinator may judge them differently.

## Findings

### Blockers (by the brief's definition)

**B1. `launch` leaves a workspace behind, with no record, when the state
directory cannot be written.** `workspace create` runs before the first
write to the state directory, and a failure of that write is not rolled
back. With the state directory read-only (fake herdr, temporary repo):

```
agent.py launch: internal error (PermissionError: [Errno 13] Permission denied: '<state>/.m9-build.json.dlbtnb89')
 workspaces left: [('w1', 'm9-build')] state: []
agent.py close: no agent 'm9-build' in <state> (`agent.py list` shows the known ones)
```

Same result when the state path is a file (`FileExistsError`) or its parent
is unwritable. A full disk would do the same. The message does not say a
workspace was left, `close` cannot close it, and the next `launch` of that
name is refused ("a workspace labelled m9-build exists"). Fix direction:
make and test-write the state directory before `workspace create`, and
close the workspace if `save_state` raises. No test covers it.

**B2. The tool writes inside the repo: `scripts/__pycache__/work_export.cpython-313.pyc`.**
`agent.py` imports `scripts/work_export.py` (at every `launch`; at `status`
and `wait` when the report is in HEAD), and Python writes the bytecode
cache beside it whenever the cache is missing or stale. Shown with a
scratch copy of the two scripts and no cache: after one `launch`,
`scripts/__pycache__/work_export.cpython-313.pyc` exists. In the repo the
cache is current today, so my strace of `status` shows only a read of it;
it will be rewritten the next time `work_export.py` changes. The path is
gitignored (`.gitignore:18`), so `tree_clean` is unaffected and no git
lock is involved; the effect is nil. It is graded blocker only because
plumbing point 7 says "nothing is written to the repo" and the brief lists
any write in the repo as one. The suite's strace test cannot see it: it
runs the tool with `python -B`. Fix direction: `sys.dont_write_bytecode =
True` before the import, and drop `-B` from the test.

### Should-fix

**S1. `--report` naming a directory counts as committed on any commit
under it.** `status m9-build --report docs/sprint` after one unrelated
commit in `docs/sprint`: `"report": {"path": "docs/sprint", "committed":
true}, "done": true`, and `wait` exits 0. Same for `docs`. `launch
--report docs/sprint` is accepted. A path that is a tree in HEAD should be
refused.

**S2. After a follow-up `prompt`, `wait` says done on the old report.**
"Committed" is measured from the launch HEAD. Round one commits the
report; the coordinator sends a follow-up; the agent goes idle without
committing anything; `wait` exits 0 with `done: true` and the old verdict.
The tool cannot know whether a follow-up called for a commit, so this is
not graded a blocker, but `status` gives the coordinator nothing to tell
the two cases apart except `commits_since`, which also counts the
coordinator's own commits (it read 1, then 2, for me while I had committed
nothing).

**S3. A brief with a NUL byte fails after the agent is started.**
`agent.py launch: internal error (ValueError: embedded null byte)`; the
workspace and agent are left open with state (so `close` works), but the
message does not say so. Refuse it with the other brief checks.

**S4. Two mutants that matter survive the tests** (see Mutants): report
committed then followed by another commit is not tested (C4a), and a
failing `git diff` counted as committed is not tested (C4f).

### Notes

- N1. With no `--report`, `done` needs only idle and a clean tree, so an
  agent that did nothing is done. Live: `wait m28-probe-build` exited 0
  with `commits_since: 0, done: true` three seconds after launch. This is
  plumbing point 7 as written and has a test; WORKFLOW's example always
  names a report. `launch` could warn when none is given for a build,
  test or fix role.
- N2. `status`, `wait`, `list` and `close` find the agent by name only. If
  the tool's workspace is closed by hand and another agent of the same
  name is started by hand, `status` reports that agent (`working`), not
  `gone`. `close` still closes only the recorded workspace id (`already
  gone`) and leaves the other alone. The state holds the pane id; it is
  not compared.
- N3. SIGTERM or Ctrl-C during `agent start` leaves the workspace with
  state (`close --force` cleans it); nothing is printed for SIGTERM.
- N4. Two `launch` runs of one name at the same instant both succeed, make
  two workspaces of one label, and the state keeps only the second. One
  coordinator does not do this.
- N5. `workspace create` answering without ids leaves the workspace with
  no state; the message says to look in `herdr workspace list`. By design.
- N6. `wait --interval nan` polls with no sleep (100 herdr calls in 2 s)
  until the time limit; `--timeout nan` never times out. Refuse non-finite
  values.
- N7. No Python traceback on any path tried (121 cases). Two blemishes:
  stdout closed early or full (`status … | true`, `> /dev/full`) adds two
  lines, `Exception ignored on flushing sys.stdout:` /
  `BrokenPipeError: [Errno 32] Broken pipe`, after the one-line error; and
  a state file with wrong types answers `internal error (TypeError: …)`
  on one line.
- N8. The brief's text is on herdr's command line while `herdr agent
  prompt` runs (`ps` shows it; the build report says so). Not stored, not
  printed.
- N9. The state directory is mode 700 only when the tool creates it; an
  existing 755 directory is left 755 (the files are still 600).
- N10. `wait` exits 1 when herdr errors three polls running. WORKFLOW's
  one-line comment lists only 0, 2, 3; the tool's docstring is right.
- N11. Docstring and feature doc say the tool "never writes in the repo"
  (see B2). Otherwise every command in WORKFLOW.md "Launching an agent in
  herdr" and `docs/features/agent-tool.md` is true of the tool as tried.

## The other questions in the brief

  said). With a record and a message: prompt errors, agent never working
  (by design). With a record and no message: S3, N3. Rolled back: `agent
  start` failing. Not created at all: every refusal, `workspace create`
  failing.

  takes a name, needs a state file of that name, and closes the recorded
  id only. `close kronk-claude`, `close w1`, `close ../m9-build`: refused,
  no herdr call. A hand-made workspace carrying a tool agent's label, with
  or without tool state: left alone.
- **Missing blocked, gone or idle-early:** blocked and gone are caught
  (live for gone, fake for blocked). Misses: N2 (same name by hand), N1
  and S2 (idle early with nothing to measure against).
