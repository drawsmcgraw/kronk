## Latency: coding and devops on Gemma's lock

The build report's reading is correct. `model_lock.server_for` gives
`127.0.0.1:11438` for `gemma-4-e4b`, so both agents now queue on the lock
the coordinator, home, research and assistant use. Voice waiters are
served first, a running generation is never interrupted, and the lock is
released between an agent's rounds, so a voice request waits for at most
one generation, not a whole turn. Dev and production are separate
processes with separate locks.

Worst case in seconds: there is no token limit to compute from. The only
`max_tokens` in config is `voice.max_reply_tokens.talkie: 120`, sent on
the speech mount only. A typed coding answer is uncapped, and the unit
sets no `-n`, so the bound is the context: 32,768 tokens. At the bench's
122.1 tok/s that is **268 s** (259 s at the 126.5 tok/s the build
measured). LiteLLM's `request_timeout` of 600 s does not cut in first.

A voice request has 25 s in total (`voice.yaml` `deadline_s`). One that
arrives behind a coding generation with more than about 3,000 tokens
left to run gets "Sorry, that took too long, so I stopped." Less if the
voice request needs its own seconds: p95 was 11.7 s, which leaves room
for about 1,600 tokens.

How likely: the largest coding completion in production history is 473
tokens (30 calls), today's were 622 and 850, which is 5 to 7 s. This is
not a new failure mode: research already shares this lock uncapped, and
`metrics.db` holds one research completion of 32,354 tokens on gemma.
M31 adds two rarely used callers to it. Before M31 a devstral generation
could not delay voice at all.
