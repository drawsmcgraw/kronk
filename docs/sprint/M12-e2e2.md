## Findings

### Blocks promotion

1. **The shopping-list item is recorded with the switch off.** The rule is
   `(?<=/shopping_list/)(?!clear(?=[?#\s"']|$))[^?#\s"']+` in both
   `telemetry.py` files. It stops at whitespace, at either quote and at `#`.
   - **tool_service's server span sees the decoded path**, so a space ends
     the match. Live, dev pair with `TELEMETRY_RECORD_TEXT=false`, request
     `remove pindlewort vashti cream from the shopping list` on
     `/dev/api/chat` (not on the dev list: 404, nothing written): Tempo,
     service `kronk-tool-service-dev`, span `DELETE /shopping_list/{item}`
     (server), `http.target` = `/shopping_list/<item> vashti cream`,
     `http.url` = `http://tool_service-dev:8103/shopping_list/<item> vashti cream`.
   - **An item whose first word is `clear` is not masked at all there.**
     Live, same setup, `remove clear dorvalex wrap from the shopping list`:
     `http.target` = `/shopping_list/clear dorvalex wrap`. (The exemption
     for `/shopping_list/clear` accepts `clear` followed by whitespace.)
   - **An apostrophe ends the match everywhere but the access line.** Live,
     switch off, `remove krelbot's snarfweed from the shopping list`:
     orchestrator log `INFO httpx: HTTP Request: DELETE
     http://tool_service-dev:8103/shopping_list/<item>'s%20snarfweed
     "HTTP/1.1 404 Not Found"`; orchestrator client span `http.url` the same
     URL; tool_service server span `http.target` =
     `/shopping_list/<item>'s snarfweed` and `http.url` likewise. httpx does
     not percent-encode `'` in a path.
   - Offline (the real apps, the wire stubbed below httpx), same result,
     plus: a double quote (`<item>"qvarginner"%20qvargtail` on the client
     span and the `httpx` line) and `#` (`<item>#qvarghashb`; the words
     after `#` are not sent to tool_service at all, which is an existing
     defect of the tool, but they are logged and put on the span).
   - What holds: a one-word item, the orchestrator's client span and
     `httpx` line for an item with spaces only (`%20` is not whitespace),
     tool_service's `uvicorn.access` line for every item tried (uvicorn
     quotes the path), `/shopping_list` and `DELETE /shopping_list/clear`
     left alone.
   - Why the fix's checks passed: `tests/test_m12_fix1_text.py` sends
     `zqxw%20florbent` and asserts `"zqxw" not in` the spans; nothing
     asserts on `florbent`. The live check used `zembrovatch`.
   - Weighing, for the coordinator: production is to run with the switch
     on, where none of this differs; the state before M12 was the whole
     item in all four places. The brief's failure condition does not carry
     that weight, so the verdict stands as written.

### The coordinator must know before running the runbook

1. **A stop while Tempo cannot be reached loses the held runs, and the
   stop then outlasts Docker's 10 s.** Offline, the real `Emitter` (batch
   processor, OTLP/HTTP exporter) with every connect refused in-process,
   E held, stop at E.end+100 s: `serve()` returned 15.21 s after the stop
   (docker would kill at 10 s); the run is in the state file's `seen` list,
   `/health` reads `emitted 1, cut_short 1, held_lost 0`, and nothing
   retries it. The only trace of the loss is the OpenTelemetry library's
   `Failed to export spans batch due to timeout, max retries or shutdown.`
   Any export fails while Tempo is down, in old code too; what changed is
   that a stop now exports every run of the last 150 s at that moment. The
   ordinary way to meet it is a host shutdown or reboot (every stack is
   stopped together) or stopping the telemetry stack first. Before either,
   H7a's wait applies: five minutes after the last spoken request.
   `docs/features/voice-capture.md:181` says a held run "is lost only on a
   hard kill".
2. **A run that ends while voice_tracer cannot reach HA's websocket for
   about nine minutes or more is never fetched, with no log line and no
   counter.** Offline: websocket away from the run's start for 30 / 120 /
   300 s: exported once (+150.8, +150.8, +300.8 s); away 560 s or more: not
   exported, every `/health` counter 0. The fetch at reconnect looks back
   600 s from the run's start and the reconnect wait is up to 60 s.
   `b50834c` behaves the same (run against a scratch worktree), so this is
   not from M12; it is listed because the brief names an HA disconnect.
3. **`ha.call_service` carries HA's play-failure message with the switch
   off.** Offline, both message shapes: span `ha.call_service`, status
   description `HAServiceError: Could not resolve qvspoken qvname to
   playable media item`. `telemetry.span()` writes the exception text there
   (ruling F6 accepts exception text). It is the message F4 took off
   `music.play_verified`, one span away, so with the switch off a literal
   play that fails still records the spoken name.
4. **H6's third check cannot pass.** `awk -v t=… '/^select\./ && $3 > t'`
   reads the third field as the timestamp. Nine of the seventeen `select.*`
   lines have a two-word state (`Okay Nabu`, `Hey Jarvis`, `Slightly
   sensitive`), so field 3 is `Nabu`, `Jarvis` or `sensitive`, which
   compares greater than any date. Run today: 9 lines printed, each last
   changed on 2026-11-16. With `$NF` in place of `$3` the same file gives
   0 lines.
5. **H8's before/after comparison reads only the first word of a state.**
   `cut -d' ' -f1,2` gives `Okay`, `Hey` and `Slightly` for those nine
   lines, so a wake word that changed from `Hey Jarvis` to another `Hey …`
   would not show. The assistant selects (`kronk`, `kronk-dev`) and every
   media player state are one word and compare correctly.
6. **H7a's two checks read 0 for up to a minute after a spoken request.**
   `/health` `held` counts runs past their Kronk join; a run still joining
   (the first 15 to 60 s) is not in it, and the `held for the correction
   window` log line is written only when the join ends. The step's own
   words (no spoken request in the last five minutes) cover it; the checks
   alone do not. With fix 1 the cost of getting it wrong is a correction
   window cut short, not a lost run.
7. **Any drop of HA's websocket closes the correction window of every run
   in flight.** Offline, a stop said 20 s after E: with no drop E leaves at
   +150.8 s marked `stop`; one drop at +40 or +100 s: E leaves then, still
   marked (the stop was already classified); a drop every 5 s: E leaves at
   +30.8 s unmarked and the stop is counted in `marks_late`. Each run is
   exported once in every case. So a flapping websocket makes the mark
   useless while it lasts, and `cut_short` counts it. `/health` `errors`
   rises by one per drop.
8. **T2's deploy check sends `What time is it?` through production
   `/api/chat`** (`scripts/deploy_tag.sh:118`), after T1 has turned text
   recording on: that sentence is the first text in production's log and
   trace. Not a household sentence; stated so it is not mistaken for one.
