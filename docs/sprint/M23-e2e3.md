## Findings

### 1. One failed item read can hand a pick back to the profile, silently (should-fix; the coordinator's call whether it is a blocker)

`build_profile` fetches each history track through `_gather_limited`,
which keeps an exception as the item's value ("one bad item never sinks a
build", from before M23). `_window_end.starts` (`tool_service/taste.py:634`)
reuses that cache: `if uri not in fetched` is false for a failed item, so
it is not read again, `_row_artist_keys` returns no artist for it, and the
row is counted as a start. When that row is a track of the picked artist
that the household once asked for by name (MA's flag is sticky) and the
pick replayed it, the window ends at that track. Every pick row stamped
after it is then the household's.

On the builder's fake MA: the household asked for one Cracker track by
name weeks ago; Kronk picks Cracker and plays 20 tracks, that one among
them.

| Build | Rows left out | Cracker history | Top of the profile |
|---|---|---|---|
| every read answers | 20 | 1.00 (the named track) | Pink Floyd |
| the first read of that one track fails | 3 | 15.71 | Cracker |

The build raises nothing and logs nothing above INFO. Reproduction, in a
scratch copy of HEAD (`tests/test_e2e3_repro.py`, not in the repo):

```python
import pytest
from tests.test_music_taste_picks import ARTISTS, FakeMA, H, KITCHEN, T, add_pick, build, household_before
STICKY = "library://track/cracker3"

@pytest.mark.asyncio
async def test_one_failed_item_read_hands_the_pick_to_the_profile(tmp_path):
    ma, failed = FakeMA(), []
    household_before(ma)
    ma.play(STICKY, "track", T - 50 * H, KITCHEN, True, artist="Cracker")   # asked for by name, weeks ago
    ma.artist_session("Cracker", T, KITCHEN, 20)                            # the pick replays it at T+960 s

    async def flaky(command, _timeout=20, **args):
        if command == "music/item_by_uri" and args.get("uri") == STICKY and not failed:
            failed.append(1)
            raise RuntimeError("Music Assistant is unreachable (TimeoutError).")
        return await ma(command, _timeout, **args)
    add_pick(tmp_path / "t.db", "artist:cracker", ARTISTS["Cracker"])
    summary, hist, _ = await build(flaky, tmp_path / "t.db")
    assert summary["kronk_pick_items"] == 20        # fails: 3
```

How likely:

- Item reads do fail. On the real data 221 of the build's 2,074 item
  reads fail every night ("The requested media item could not be found.",
  all `pandora://track/…`). None of those rows is user-initiated, so none
  can trigger this.
- The copy of MA's `media_progress` holds 35 user-initiated track rows (28
  YouTube Music, 7 library). Each is a track a later pick of its artist
  can replay.
- On today's data no such track sits in any pick's start reads (0 for all
  ten picks), so no single failed read changes today's profile. I failed
  each candidate in turn in scratch: there were none to fail.
- A profile built wrong this way is rebuilt the next night.

Why should-fix and not blocker: it needs four things at once (a sticky
track of the picked artist, replayed by the pick, inside the window, whose
read fails that night); the resulting profile counts fewer of the pick's
rows than `ff8a7a5` does (17 of 20 against 20 of 20); and the second
test's finding 7 already recorded that one failed item read is swallowed,
as a note. What is new is that fix 3 turns one lost item into a lost
pick. If the blocker line is read to include a single failed read, this
is a blocker.

Size of the fix: in `starts`, read the item again when the cached value is
not a dict (`if not isinstance(fetched.get(uri), dict)`). A read that
fails there raises, the build fails, the old profile is kept and the loop
logs it at ERROR, as for every other read `_window_end` makes.

### 4. What the margin costs (note)

Ruling D is sound against how MA stamps rows (source read in the
container, `2.11.0b5-kronk.9`):

- a track is stamped when the tracker sees the queue's current item
  change or the play stop, and never for under 5 s played
  (`_handle_playback_progress_report`);
- `mark_item_played` writes the playlog only when the item is not
  playing, at `utc_timestamp()`;
- a station or dynamic playlist is marked when it is enqueued
  (`queue_loader.py`, `user_initiated=True`).

So a track the household starts after the pick is stamped 5 s or more
after it, and the track the pick replaced is stamped at about the pick's
own second. The one start a margin misses is a station or playlist
started within 5 s of the pick's truncated second.

On the real data (scratch copies; counts and times only):

| Table | User-initiated rows in `[int(ts), int(ts)+5)`, ten picks | Nearest after a pick |
|---|---|---|
| `media_progress` | 0 | 61.6 s (pick 14) |
| `play_history` | 0 | 5.6 s (pick 16), 6.6 s (pick 13) |

No household start falls inside a margin. The nearest is the 2026-11-08
bench station, 6.2 s after pick 16's truncated second: 1.2 s to spare.
Across the whole `play_history`, 16 pairs of user-initiated rows on one
queue are under 5 s apart (of 197 rows), so back-to-back starts do happen.

What a missed start costs, on the fake: the household starts a station
3 s after a Cracker pick, then asks for Cracker by name two hours later.

| Station started | Rows left out | Cracker history |
|---|---|---|
| T+3 s (inside the margin) | 11 | 0.00: the household's request is dropped |
| T+6 s | 0 | 10.47 |

That is the stated limit (the picked artist asked for by name) reaching a
case it would not otherwise reach. `music-taste.md` says a start inside
the margin is missed; it does not say what follows from it.
