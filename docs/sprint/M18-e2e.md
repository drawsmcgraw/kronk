# M18 end-to-end report: an upgrade cadence

**M18 FAILS.**

End-to-end test agent, 2026-11-18 (UTC), branch `refactor`, build
`2f5b235..edaf64a`. Tested against `docs/sprint/M18-criteria.md`; the build
report was read as claims. Nothing was upgraded, installed, sent or
restarted by this test.

Why it fails, in one paragraph: on the real system the monthly run cannot
start a single component. Its own baseline replay sends chat requests
through nginx and leaves runs held in voice_tracer, and the per-component
"house busy" check that follows reads both as the house being busy
(finding B1; seen live). The run then ends "nothing applied" with no
notice, seven nights in a row, and closes the month silently. Behind that
are two failures the brief lists by name: a notice that says "ROLLBACK
FAILED" when no rollback was attempted and nothing was deployed (B2), and a
killed run that leaves a pin commit ahead of what runs, or Home Assistant
stopped, which the next run reads as "CURRENT, nothing to upgrade" and
reports to nobody (B3). The rules themselves are sound: no case picked a
major release, an excluded component or a floating pin.

Times are UTC as `date -u` printed them. The session's clock jumped from
05:35 to 11:37 between the second replay and the rest of the work; both
halves are the same session.

## Findings

### Blocks installing the timers

**B1. The run declares the house busy because of its own replay.** After
the declines pass, `minor_run` runs the baseline replay, then `apply_one`
calls `house_busy()` again before each component. The replay's requests
reach nginx as `POST /dev/voice/api/chat`, which `CHAT_ROUTE` matches, and
voice_tracer holds the replay's runs for its correction window. The build's
`FakeOps` has a static, empty nginx log and the rehearsal stubbed the log
and the probe, so neither saw it.

- Live, read-only: `docker logs --since 4m kronk-nginx-1` during the replay
  showed `11 "POST /dev/voice/api/chat 200`. `scripts/upgrade_minor.sh
  --dry-run` at 11:44:15, 114 s after a two-request replay batch ended,
  printed: `a real run now would DECLINE: … voice_tracer holds 2 run(s) in
  the correction window; 2 chat/voice request(s) in the last 5 minutes`.
- Offline, the build's fake plus a log that records the run's own requests
  (harness 2): every component `not started: house busy: 61 chat/voice
  request(s) in the last 5 minutes`; no commit, no notice; `done:
  not_started`. Seven nights: seven baselines, seven replays, `attempts 7,
  done True`, zero notices, zero warnings.
- The same holds between components: each verify ends with a replay, and
  `deploy_tag.sh deploy` itself posts to `/api/chat`.
- Mutant d21 (the per-component busy check removed) survives the test
  suite: no test exercises that check at all.

**B2. A notice says "ROLLBACK FAILED" when no rollback was attempted.** Any
`StepFailed`, `RulesError` or `OSError` raised inside a component becomes
outcome `rollback_failed`. Input: litellm rolled back at 08:30 (tag
`upgrade-20261201-litellm` stays, by design); the operator reruns the same
day with `--ignore-month`, as the feature doc suggests. Result: commit
`upgrade: litellm v1.88.1 -> v1.88.6` is made, `git tag` fails, and the
notice reads `Kronk upgrade: ROLLBACK FAILED (litellm)` / `ROLLBACK FAILED,
needs you (the run stopped inside this component: git tag
upgrade-20261201-litellm: fatal: tag 'upgrade-20261201-litellm' already
exists)`. Nothing was deployed and nothing was rolled back; git is left
with the pin at v1.88.6 while v1.88.1 runs, and the text does not say so.
Later runs are blocked until `ack`; after `ack` the next run reads v1.88.6
as CURRENT (B3's second half).

**B3. A run killed mid-component is invisible to the next run.** The
process dying (reboot, OOM, `systemctl stop`, the unit's 4 h timeout)
leaves no status beyond the attempt count. The next night's plan reads the
already-committed pin as `CURRENT`, finds nothing to do, marks the month
done and sends nothing; the decline checks, which would notice HA down, are
not reached when there is nothing to do.

| Killed at | State left | Next night |
| --- | --- | --- |
| litellm: after the pin commit, before the tag | git v1.88.6, runs v1.88.1, no tag | `CURRENT`, "nothing to upgrade", month done, no notice |
| litellm: after the tag, before the deploy | as above plus the tag | same |
| litellm: deployed, during verify | v1.88.6 runs unverified | same |
| grafana: after the pin commit, before the pull | git 13.2.6, runs 13.2.4 | same |
| HA: after the pin commit, before the pull | git 2026.5.5, runs 2026.5.4, `kronk/ha-rollback:2026.5.4` tag | same |
| HA: after `docker stop`, before `compose up` | **HA stopped** (`restart: unless-stopped` does not bring it back, also not after a reboot), git 2026.5.5 | same: "nothing to upgrade", month done; HA stays stopped |
| grafana: in the rollback, pin restored in the file, not committed | staged change | declines "working tree not clean" (correct) |

A pin commit without its deploy also means the next ordinary deploy of the
Kronk stack, or the next `compose up` of HA or telemetry by hand, brings up
the new version unverified. HA has no 2026.5 patch left, so the HA rows
cannot happen until HA has had a major upgrade.

### The coordinator must know before installing

**K1. A failed pull restarts Home Assistant for nothing.** `ha_up` returns
an error at `docker pull` (before HA was touched); `rollback()` then runs
`docker stop -t 120 homeassistant` and `compose up -d`. Harness 5: mutating
calls `tag, pull (exit 1), stop, compose up`; notice `rolled back to
2026.5.4 (docker pull … failed)`. The same happens when the tag step fails.

**K2. H7b is not in the code.** M12's runbook re-checks, before the stop,
that `/home/drew/kronk-voice-recordings` exists (`create_host_path: false`:
Docker refuses to create HA without it). The script checks the config hash,
not the directory. If it is missing, the upgrade's `up` fails after the
stop, the rollback's `up` fails the same way, and HA is left stopped. That
ends as `ROLLBACK FAILED`, exit 2, a pending notice and the `/services`
warning, so it stops and says so; but the text reads `2026.5.5 may still be
r…` (cut at 200 characters) and never says HA is down. Also not in
`ha_checks`: H7's mount check and HA's "not shut down cleanly" log line.

**K3. A registry that answers nonsense kills the whole run.** Only
`LookupFailed` is caught in planning. A Docker Hub tag list that is a JSON
list or string, a GitHub list of non-objects, `tag_name` or `published_at`
as a number, a ghcr token answer that is a list, a ghcr tag list that is
HTML, or a body cut short (`http.client.IncompleteRead`) raises
`AttributeError`, `JSONDecodeError` or `IncompleteRead` out of `minor_run`:
traceback, no status, no notice, the attempt counted, healthy components
not upgraded either. Seven such nights close the month silently. Nothing is
changed. HTML from Docker Hub, a GitHub rate-limit object and a timeout are
handled (that component is skipped and the others go on).

**K4. A month of "not started" ends silently.** HEAD carrying undeployed
work (true today: `orchestrator/main.py`, `services.html`,
`upgrades_api.py`) makes every Kronk-stack component "not started". Seven
nights of that (each with a full baseline): no notice, no warning, summary
`Kronk upgrade: nothing applied`, month done. A month of declines does
notify; this path does not.

**K5. Every Kronk-stack component upgrade is a full production redeploy.**
`deploy_tag.sh deploy` of a new tag changes the release directory, so every
service with a bind mount is recreated (orchestrator, tool_service,
voice_tracer, nginx, litellm, searxng), and a rollback is another. Two
Kronk components in one night can mean four restarts of production.

**K6. A missed 03:30 runs at boot, at any hour.** `Persistent=true` (as the
criterion asks) fires the monthly run at the next start of the user
manager. The run still declines on playing players, busy pucks and requests
in the last five minutes, but an HA restart at 19:00 after five quiet
minutes is possible. `After=docker.service network-online.target` has no
effect in a user unit.

**K7. The quarterly check takes no lock.** `major_run` reads and writes
`status.json` and commits without `data/upgrades/lock`. Overlapping a
monthly run (a boot catch-up of both timers) it can overwrite that run's
status, including a failed-rollback block. `load_status` also reads a
corrupt file as empty, which drops the block; the API warns on a corrupt
file, the script does not.

**K8. Nothing protects against a deploy started during a run.** The run
checks for a running `deploy_tag.sh` once at the start; `deploy_tag.sh` does
not look at the upgrade lock.

**K9. `inert_paths` holds, with one note.** Nothing on the list reaches a
Kronk container: the build contexts are `orchestrator/`, `tool_service/`,
`voice_tracer/` and `tests/` (only `voice_corpus.jsonl` and
`fixtures/music_snapshot.json` are copied), the bind mounts are `nginx/`,
`searxng/`, `data/`, `secrets/`, `magicmirror/`, `ops/`, `litellm/`,
`kronk-context.md`. `scripts/*` is inert for the containers but includes
`deploy_tag.sh` and `config_check.py`, which the run executes from HEAD.
For telemetry and HA the guard is the compose config hash, which does not
cover the contents of bind-mounted files (`telemetry/*`): a recreate loads
whatever is in the working tree. The loader accepts `deploy = "compose"`
with `project = "kronk"`, and accepts `bgutil-pot-provider` (the MA stack)
as `auto`; only the names `music-assistant` and `llama.cpp` are guarded.

## Git behaviour (scope 5)

Author and committer `Kronk upgrade_minor <upgrade_minor@kronk.invalid>`,
passed with `-c` per command; no `git config` call. Subjects `upgrade:
<name> <from> -> <to>` and `upgrade: roll back <name> <to> -> <from>`; body
names the release URL and the run log. Tags `upgrade-<YYYYMMDD>-<name>` for
Kronk-stack components only. Subcommands used: `rev-parse`, `status`,
`diff`, `add`, `commit`, `tag`. No `push`, `--force`, `--amend`, `reset`,
`rebase`, `checkout`, `stash`, `clean`; no remote touched. A rollback is a
new commit. Mutant v29 (`git tag --force`) survives: no test would notice a
forced tag.
