### S1. `build` can be made to accept a non-empty directory

Criterion 3: "refuses a non-empty directory". It refuses one named
directly (a file, a hidden file, an empty `lib/`, a dangling link inside:
exit 2, docker never called). Two ways round it, both run in scratch with
a fake `docker`:

- **A symlink to a non-empty directory.** The emptiness test is
  `find "$dir" -mindepth 1 -maxdepth 1 -print -quit`; GNU find does not
  descend into a symlink given as its start point, so it prints nothing
  and the directory counts as empty. `build <link>` then extracted into
  the target, beside a `notes.txt` already there, **replaced** an existing
  `lib/libroctx64.so.4.1.70200` (content `OLD`), wrote `MANIFEST` and
  exited 0. With an unlisted file already in `lib/` it exits 1 at
  `check_extracted`, after overwriting. The same directory named with a
  trailing slash (`<link>/`) is refused.
- **`<non-empty>/new/..`**: `[ -e ]` is false because `new` does not exist,
  so the test is skipped; `mkdir -p "$dir/lib"` then creates `new` and
  extracts into `<non-empty>/lib`. Exit 0.

Why it matters here: `~/services/rocm-7.2` is a real directory today, but
moving it to another disk and leaving a symlink is an ordinary thing to do,
and a later `build ~/services/rocm-7.2` would then extract over the
libraries three units have loaded instead of refusing. Fix direction:
resolve the path first (`realpath -m`), then test.

Nothing escaped the directory given: a tar stream with `../../x`, an
absolute member, a symlink followed by a member through it (absolute and
relative), and a hard link to an outside file all left the outside
directory untouched (GNU tar strips or refuses them; exit 3 or 1, no
manifest). A stream with an extra top-level file or a `hipblaslt`
directory is refused by `check_extracted` (exit 1, no manifest). A setuid
member is extracted with its mode and recorded as such (`-p`); from the
pinned image that cannot occur.

## What the maps check cannot show

`/proc/<pid>/maps` lists files a process has mapped. rocBLAS's kernel
data (`rocblas/library`: the `.dat` selection tables, the `.hsaco` and
`.co` kernel objects) is opened, read and closed. None of the three units
has a mapping or an open descriptor under any `rocblas/library`, so "no
process maps a file under Ollama's directory" says nothing about which
copy of that data a unit read. Access times do not help either: both
filesystems are `relatime`, every file in both directories was hashed
today, and a later read does not move the time again within a day.

What evidence there is, strongest first:

1. **Observed in a process of mine, not in the units.** `strace` on a
   scratch process that loads `librocblas.so.5` from the scratch copy
   (the same bytes as the live directory, by manifest) and calls
   `rocblas_initialize()`: 151 data files opened, all under
   `<scratch>/lib/rocblas/library` (the lazy gfx1151 `.dat` first), after
   three probes that did not exist (N6). No path under an Ollama
   directory, `/opt/rocm` or `hipblaslt/` was tried. So this build of
   rocBLAS finds its data from the location of the `librocblas` it was
   loaded from, and falls nowhere else when that succeeds.
2. **Each unit maps `librocblas.so.5.2.70200` from
   `~/services/rocm-7.2/lib`** and its environment holds no ROCm or
   Tensile path variable (read from `/proc/<pid>/environ`).
3. **The texts.** All 1,793 data files differ between the two sides, and
   two rows changed text exactly at the dev restart and stayed changed.
   That fits new kernels (or new host libraries); it does not prove
   which.
4. `/opt/rocm` does not exist on the host, so the compiled-in fallback
   has nothing to find.

That the running units read their data from the new directory is
therefore an inference from 1 and 2. The proof is Drew's rename.
