## Notes

1. **`KRONK_TZ=localtime` loads and is UTC.** The image's zone directory
   has a `localtime` entry, so the name is a valid key and gives "4:52 AM
   UTC" with no warning. The line says UTC, so nobody is told a wrong
   zone, but it is the old behaviour by a plausible-looking value.
   `posixrules` loads as Eastern.
2. **A zone with no abbreviation prints its offset.** `Etc/GMT+5` gives
   "11:52 PM -05", `Factory` gives "4:52 AM -00". Correct hour; the model
   gets a number where it had "EST".
3. **`scripts/coordinator_model_bench.py:226`** takes the expected weekday
   from the host's local clock while the prompt it scores now follows
   `KRONK_TZ`. They agree on this host. They would differ if the bench
   ran on a host in another zone, or with `KRONK_TZ` set to one.
4. **A period written with `Z` is labelled in UTC hours** ("5 AM" for
   `05:00:00Z`). That is the ruling (the offset it arrives with). The
   Weather Service sends the place's offset on `forecast/hourly`; if it
   ever sent `Z` the labels would be five hours off again, with no test
   to say so.
5. **Minutes are dropped**: `23:30+05:30` is "11 PM". The Weather
   Service's hourly periods start on the hour for US offsets.
6. **Promotion: check production's first hourly label after the deploy.**
   The forecast is kept in `/data/weather_cache.json` and loaded at
   start. The refresh loop fetches at once on start, so the UTC labels
   are normally gone in seconds. If that first fetch fails, the old
   summary (UTC hours) is served beside the new EST clock until a fetch
   succeeds or the copy passes `weather_context.max_age_s`.
7. **The hourly list is as old as the cache** (up to an hour): at 22:58
   its first label can still be the 10 PM hour fetched at 22:01. So
   before M35; the prompt now states the right clock beside it.
8. **One warning per name per process**, not one per process: a
   `KRONK_TZ` changed between bad values would warn once each. The value
   is fixed at container start, so it is one in practice.
