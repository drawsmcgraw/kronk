## Findings

Severity: blocker, should fix, note. Paths are under `/tmp/kronk-m16-e2e`

### Blockers

**1. A recording named like the job's temporary file is destroyed, and the
run reports OK.** Blocker (criterion 10; loss of a recording).
Reproduce: a run directory holding `.kronk-archive.tmp` (5,000 bytes) and
`01_b.wav`, both older than the age. One archive run: `Moved 2 recording(s)
(11.0 KB) … recordings archive 6.0 KB (1 file)`, exit 0. Locally nothing is
left; on the destination only `01_b.wav`. Cause: the first file is copied to
`<run>/.kronk-archive.tmp` and "renamed" onto itself, so the finished file
has the temporary name; the next copy into that directory (same run or any
later run) starts with `if os.path.lexists(tmp): os.unlink(tmp)`
(`copy_verified`). Home Assistant does not write that name; anything else
that does loses the file silently.
Fix: `scan_recordings` reports and skips a source file whose name is
`ARCHIVE_TMP` (as it does a symlink); a test with that name beside a second
file.

**2. A file replaced after its verify and before the end-of-run delete is
deleted without being archived, and the run reports OK.** Blocker (ruling 6:
only a file whose copy has the same size and SHA-256 may be deleted).
Reproduce: `run1/01_a.wav` (4,000 bytes) and `run2/01_big.wav` (1.5 GB),
both old. While the big file is being copied, replace `01_a.wav` by rename
with new content. Result: `Moved 2 recording(s)`, exit 0; locally nothing;
the destination holds the first content (`c27dbf1b…`), the replacement
(`d03d115f…`) exists nowhere. Cause: all deletes happen in one container at
the end of the run, by path, with no re-check; the window is the rest of the
run (minutes on a first run over SMB). The same gap in the other direction:
a destination file that vanishes after its verify does not stop the local
delete (fault injected after the rename: `Moved 2`, destination 0 files).
HA does not rewrite a week-old recording; a restore, a copy back for
labelling or a hand edit during a run would.
Fix: pass each path's expected size, mtime and inode to the delete script
and have it `stat` and compare before `rm`; before building the delete list,
`lstat` the destination file again (exists, same size). A test that swaps
the file between `copy_verified` and `remove_recordings`.

**3. A symlinked directory under `<dest>/recordings` can make the archive
verify a recording against itself and delete it.** Blocker by the brief's
definition; not reachable on the default destination unless the share shows
symlinks (a local or USB `--dest` can).
Reproduce: `dest/recordings/devA/kronk/2026-10/run1` is a symlink to the
source run directory `rec/devA/kronk/run1`. One run: `Moved 1 recording(s)
(5.0 KB) … Written this run: 0 B … recordings archive 0 B (0 files)`, exit
0; the file is gone from both places ("already on the destination with the
same SHA-256" was the file itself). With the device directory symlinked to
an outside directory, the copy is written into that directory instead
(nothing lost, the totals say 0 files).
Fix: refuse a destination path with a symlinked component below
`<dest>/recordings` (`lstat` each level in `mkdir_private` and before the
"same" test), and treat `os.path.samefile(final, source)` as a conflict.

### Notes

14. **Mount flag.** The default is recognised by `os.path.normpath(dest) ==
    "/mnt/nas-backup"`: `/mnt/nas-backup/`, `/mnt/./nas-backup` and
    `/mnt/x/../nas-backup` are flagged; `//mnt/nas-backup` and any
    subdirectory (`KRONK_BACKUP_DIR=/mnt/nas-backup/kronk` in `backup.env`)
    are not, and would be written while unmounted if the directory exists.
    Flagging any path at or under the default would close it. A flagged path
    that is a real mount (a tmpfs) is accepted; one that is not is refused
    with nothing written (exit 2).
15. **The upgrade lock.** No deadlock is possible: `upgrades.py` takes only
    its own lock and never looks at the backup's. The backup probes the
    upgrade lock with `LOCK_SH | LOCK_NB` and releases it at once, so the
    docs' "never taken" is not exact: an upgrade run (or `deploy_tag.sh`'s
    `flock -n`) that tries in that instant would decline. The backup closes
    its own lock while it waits, so it starves nothing; it declines after 30
    minutes. The upgrade run never waits for a backup (documented). Two
    backup jobs at once: the second declined (exit 3, DECLINED notice) or,
    with a wait, ran after the first.
16. **`Persistent=true` after a powered-off night** fires the job at the
    next start of the user manager, possibly before the `nofail` share is
    mounted and before HA can deliver a notice: the run then fails (exit 2)
    and is not retried until its next date (a month for the config backup);
    the 09:30 stale check reports it. Read from the unit files; not run (no
    install). A short wait for the mount point in the job would cover it.
17. **`/services` gaps.** A job that has never succeeded is not shown as
    stale from the status file (`last_ok_at` absent is skipped), though the
    feature doc says a check that never runs still shows a stale job; with
    no status file at all the card is green. `check.warnings` given as a
    string is shown one character per warning. Warning text is escaped on
    the page (`esc(desc)`).
18. **"Destination full" stops the run at the first file that does not
    fit**, so one oversized file early in the order blocks every later file
    on every run (a 30 GB sparse file before three small ones on a 4 MB
    tmpfs: nothing moved, twice). The temporary copy was removed each time.
19. **The size guard checks after the write**: an oversize tar reaches the
    destination under its temporary name, is verified, then removed.
20. **A symlinked recordings root is followed** (`--src` a symlink: the
    files are read and deleted in its target). A bad setting such as
    `KRONK_BACKUP_KEEP=abc` ends the job with exit 1 before any notice or
    status. A declined job rewrites `status.json` without holding the lock
    (not reproduced as a lost update). The end notice's "remain local"
    counts only files at recording depth.
21. **CLAUDE.md** says the NAS account is "installed as the root-only
    `/etc/kronk/nas-backup.cred`"; today `/etc/kronk` holds only
    `nas-music.cred` (the install is Drew's, pending).
22. **Build report counts.** "36 unit files, 34 identical": the host has 29
    unit files, 28 identical. "29 GGUFs": `models.tsv` lists 28 today. The MA
    `settings.json` is 63,228 bytes here (63,229 in the report; it changes).
23. **Runbook, smaller gaps.** `hottub_monitor/.venv` (the monitor's unit
    runs from it) is not rebuilt by any step; step 10 starts the llama and
    Whisper units but no `kronk-*` service or timer (they start at the next
    boot); `tar -xzf` leaves the top directory at the umask's mode inside
    the 0700 `~/restore` and `.env` at its source mode 0664; the "keep the
    current state first" tar is written root-owned 0644 and holds HA's auth
    store; a same-day `.2` tar unpacks into the same directory name as the
    first. `HA_NAMES` is a fixed list: a later `custom_components/` or
    `www/` in HA's config would be left out without a word (neither exists
    today).
