## Findings

### 1. Blocker: a run that reaches the record after its neighbour was joined

`audio_joins()` waits while a row in the target's set is younger than
`FINAL_S`. It cannot wait for a row that is not in the record yet. Two ways
a run arrives already final, both inside this fix round:

**The read budget (F8).** `read_window()` reads a day per search and stops
on the budget. A day mark falls between run A and run B, seconds apart,
one recording fitting both. The budget ends after A's day. A is old, so it
is final at once; its set holds only A; stored `certain`. B comes with the
next run: `ambiguous`. A keeps `certain` for good (`audio_tried_at` is
set).

Shown: `test_f1_a_first_read_cut_by_its_budget_between_two_runs_on_one_recording`
(xfail). A at a day mark minus 4 s, B at the mark plus 3 s, the recording
at plus 4 s, four days old. Stored `A: certain, B: ambiguous`; the join
over both says `ambiguous, ambiguous`. The same holds for any catch-up
read longer than a day that the budget cuts, and for the hourly check's
passes.

**The hourly check's take (F4).** A run the main read missed is inserted
up to an hour later, beside a row already joined.

Shown: `test_f1_a_run_the_hourly_check_takes_beside_a_row_already_joined`
(xfail). Same stored result.

**A run that reaches Tempo later than the premise** ends the same way:
`test_f1_note_a_run_that_reaches_tempo_after_final_s_is_ambiguous_beside_a_stored_certain`
(passing; it records what is stored). The ruling accepted that premise;
the two cases above do not rest on it.

One cure covers all three, for the coordinator to weigh: when a row is
inserted already final, clear `audio_tried_at` for the rows of its set, so
the set is joined again whole. The audio columns are not published and
raise no `seq`.

### 2. Should-fix: `--remove` while an export holds the lock removes nothing and exits 0

`main()` returns 0 with "another export holds the record's lock; this run
does nothing" for any run, a removal included. The timer fires every 60 s
and a run may hold the lock for up to 43 s. A person who removes a guest's
run and checks `$?` is told it worked. The log line is the only sign.

Shown: `test_remove_while_an_export_holds_the_lock_does_not_exit_0_with_nothing_removed`
(xfail). A removal should wait for the lock or exit 1.

### 3. Should-fix: `TEMPO_TIMEOUT_S` does not bound a request, so 43 s is not a bound

`urlopen(url, timeout=5)` limits each socket wait, not the request. A
loopback server answering one byte a second: `http_get_json(url, 5.0)`
returned after 13.0 s (scratch script, not in the suite: tests open no
sockets). The budgets stop a request from *starting* late; they do not end
one. A Tempo that dribbles passes 43 s and the unit kills the run at 50.
The kill is safe (nothing written, the transaction rolled back), but the
status file then goes stale instead of saying why.

### 4. Note: the wait for the record is outside the 43 s

After Tempo, `BEGIN IMMEDIATE` waits up to `BUSY_TIMEOUT_S` (10 s) for a
person's open transaction. 43 + 10 = 53 > 50: with Tempo at its worst and
a person holding the record, systemd kills the run before F9's "database
is locked" reaches the status. With Tempo as it is (0.3 s) the wait fits
with room.

### 5. Notes

- A recording that appears after the row was tried is never joined
  (`test_f1_note_a_recording_that_appears_after_…`). Home Assistant closes
  the WAV inside the run, so this needs a file copied in later.
- A run with a nonsense end (ten days long) holds the join of every later
  row with a recording until that end plus `FINAL_S`
  (`test_f1_note_a_neighbour_with_a_nonsense_end_…`). No wrong answer is
  stored. voice_tracer cannot export such a run (840 s from its start).
- `--remove` with `--check-now` ignores `--check-now` without a word;
  `--why` without `--remove` likewise.
- `--init` while another run holds the lock also exits 0 having made
  nothing. The timer is not installed at the first export, so it cannot
  happen then.

## F1: orders and shapes

The oracle in every test is `voice_label_sheet.join` over every row and
recording of the finished record. All within the premise unless said.

| Shape | Orders | Result |
| :-- | :-- | :-- |
| Three runs on one recording | all 6, one an export | join's answer: ambiguous ×3 |
| Chain: A, B share recording 1; B, C share recording 2 | all 6 | join's answer (ambiguous: two pairings tie) |
| The chain with a third recording only C fits | all 6 | join's answer: certain ×3 |
| A final and waiting for B; C arrives beside B | one | A, B, C wait (`audio_waiting` 1, then 2); joined together when C is final |
| B of the chain removed before the join | all 6 | A and C as the join over all three rows; B never written |
| B removed after the join | all 6 | no stored join moves |
| A neighbour 830 s long (the longest the tracer exports) | one | A waits until the neighbour's end + 900 s, then the join's answer |
| A recording that appears after the row was tried | one | stays `none` (note 5) |
| A neighbour that never becomes final (ten-day end) | one | waits, no wrong answer (note 5) |
| A read cut between the two runs | one | **wrong for good** (finding 1) |
| A run the hourly check takes | one | **wrong for good** (finding 1) |

"A row that waits for ever": not reachable by the constants. A row waits
only on a row in the record, and every row's end is at most 840 s after
its start, so the longest wait is the neighbour's end plus 900 s.

**The premise.** It was not pinned by any test. It is now:
`test_f1_the_premise_voice_tracers_export_limit_is_under_final_s`. The
tracer's limit counts from the run's *start* (`voice_tracer/main.py`,
`_emit`: the first span's age), so a run's own length is inside it. A run
that fits A's recording starts at most 7 s after A ends. With the batch
delay and exporter deadline that `tests/test_m12_fix1_tracer.py` counts:
840 + 5 + 10 + 7 = 862 < 900. The margin for Tempo's search to show the
run is 38 s.

**A run later than that.** voice_tracer does not send it at all
(`too_old`, counted on `/health`): it has no row, which is rule 10. If
Tempo itself shows a run late, the result is finding 1's.

## F8: the arithmetic

By the constants: no request of the main read starts after 20 s, of the
trace reads after 30 s, of the check after 38 s. A request has 5 s. The
last one starts at 38 s at the latest and ends by 43 s. The unit's
`TimeoutStartSec` is 50 (`test_f8_the_budgets_and_the_unit_by_the_constants`
reads it from the unit file).

One case: `test_f8_every_request_at_its_whole_timeout_ends_inside_43_s`.
Every request takes its whole 5 s and then answers, six runs: no request
starts later than 38 s into its run and none of the runs passes 43 s on
the budget clock.

What the arithmetic leaves out: a request can outlast its 5 s (finding 3),
and the wait for the record adds up to 10 s (finding 4). The rest of a run
(the recordings scan, the transaction, the publish) was 0.07 s on the
4,000-row record.
