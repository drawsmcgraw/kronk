## Findings

### 1. The five seconds are not a limit on the whole check

Request: `GET http://127.0.0.1:8103/http_check?url=http://172.18.0.1:18770/drip`.
The listener sends the status line, then one header every 2 s, and
finishes after about 8 s.

```
http://172.18.0.1:18770/drip -> {"url":"http://172.18.0.1:18770/drip","ok":true,"elapsed_ms":8010,"status":200,"redirects":[],"final_url":"http://172.18.0.1:18770/drip","headers":{"server":"M5E2E2/1","content-type":"text/html","content-length":"2"}}
```

Cause: `client.stream("GET", current, timeout=remaining)`
(`tool_service/main.py:607`). In httpx that number is the limit for each
connect, write and read, not for the request. A server that keeps sending
a little, with no gap of five seconds, holds the check open for as long as
it likes. The budget is checked only between hops (`:598`).

The code comment (`:528-530`, "inside the same five-second budget") and the
feature doc (`docs/features/fetch-address-block.md:51`, "Five seconds for
the whole check, redirects included") say more than the code does.

Why this is not counted as a failure: criterion 10 says "five-second
timeout", and that timeout exists and fires (5003 ms on a silent server,
5003 ms in total across a slow redirect and a slow page). The line is the
same at `bd04608`, so the first test passed criterion 10 on the same code,
and change 1 did not touch it. It is a judgement; the coordinator may see
it differently. The effect is small on this system: a slow or hostile
device can make one devops tool call take longer than five seconds, up to
the orchestrator's own tool timeout. A fix would be one
`asyncio.wait_for` (or `asyncio.timeout`) around the loop.

### 2. An unparseable `Location`: the change report's claim does not hold live

Claim (`M5-change1.md`, "The e2e observations", 4 (a)): an unparseable
`Location` (`http://[::1`) "is now reported, not followed, with
`invalid URL: …`". `test_redirect_with_an_unparseable_location_is_reported_not_followed`
asserts `ok` true, status 302, and the note.

Live, with a listener that answers 302 with `Location: http://[::1`:

```
http://172.18.0.1:18770/to?http%3A%2F%2F%5B%3A%3A1 -> {"url":"http://172.18.0.1:18770/to?http%3A%2F%2F%5B%3A%3A1","ok":false,"elapsed_ms":10,"cause":"network","error":"network error: RemoteProtocolError: Invalid URL in location header: Invalid port: ':1'.","redirects":[],"final_url":"http://172.18.0.1:18770/to?http%3A%2F%2F%5B%3A%3A1"}
```

Cause: httpx 0.27.2 parses the `Location` header itself, even with
`follow_redirects=False`, and raises `RemoteProtocolError` from
`client.stream(...)` before the handler sees the response. The handler's
`except httpx.HTTPError` (`main.py:612`) reports it. The new
`except (httpx.InvalidURL, ValueError)` branch (`:620`) is not reached for
this input with the real client. The unit test passes because `FakeClient`
hands back the response without that step. Checked with the test venv's
httpx (same version as the container's) against my listener:

```
httpx 0.27.2
get raised RemoteProtocolError | Invalid URL in location header: Invalid port: ':1'. | RequestError: True | HTTPError: True | InvalidURL: False
stream raised RemoteProtocolError | Invalid URL in location header: Invalid port: ':1'. | RequestError: True | HTTPError: True | InvalidURL: False
```

What is right: no 500, the call is audited, nothing is followed, and the
message names the header. What is wrong: `ok` is false and the cause is
`network` for a host that answered; the 302 and the `Location` value are
not in `redirects`. Not counted as a failure: no criterion covers a
malformed `Location`, and the outcome is safe.

The same step means the change report's note under "Not done" ("`/fetch`
and an unparseable `Location` … gives a 500") is probably also not what
happens live: `client.get` would raise `RemoteProtocolError`, which is a
`RequestError`, and `/fetch` returns `network error: RemoteProtocolError`
for that. I could not test it live on `/fetch` (a public first hop that I
control does not exist here), so that is inferred from the httpx check
above, not observed.

### 3. `no_network` on the async path with a literal address raises an `ExceptionGroup`

The fixture stops the connection in every case I tried. For a literal
address on the async path (which is what `/fetch` and `/http_check` use),
the `NetworkBlocked` comes out of `socket.connect` inside anyio's connect
task group, so the test sees
`ExceptionGroup: unhandled errors in a TaskGroup (1 sub-exception)` with
`NetworkBlocked` inside it. The test still fails loudly and nothing is
sent. `pytest.raises(NetworkBlocked)` does not match it. The repo's own
`test_the_network_guard_is_on_for_this_module` uses a name (`nas.test`)
on the async path, which is stopped earlier, at `getaddrinfo`, and raises
`NetworkBlocked` directly. No change needed; worth one line in the fixture
comment.
