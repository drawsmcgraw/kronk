overlaps a read is "tried both ways", so its "new N" excuses N rows
whichever side of the read its commit fell on. The fix report describes
the rule in its B1 section, but not as something that lets a write
through. The window is small: a run lasts about 0.1 s and the margin is
0.2 s on each side, so about 0.5 s in each 60 s at each read, and the
run must have listed a new voice run. Inside it, a plain insert of that
many rows from a subprocess passes, and that is the write `M30-e2e6` B1
was about (a row a test inserts stays, in the file that is backed up).
The last two lines need a writer that undoes the timer's own row first;
I list them for completeness.

What would close them is the coordinator's to choose. For the fence:
compare by device and inode instead of by resolved path (it covers the
hard link), wrap `os.link`/`os.symlink` and the `sqlite3.Connection`
and `io.FileIO` classes, and resolve a relative name against `dir_fd`
when one is given. For the overlap: read the start snapshot again when
the journal shows a run within the margin of it, so that no run
overlaps the start read.
