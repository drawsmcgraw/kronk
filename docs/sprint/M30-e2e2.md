## The blocker

### 1. The audio join depends on which run reached Tempo first (B7, plumbing 6)

Where: `scripts/voice_runs_export.py`, `export()`: the join is made once,
for the rows a read sees for the first time (`news`, `targets`), against
those rows and the rows already in the record (`nearby`). A run that has
not reached Tempo yet is not in the pool. `audio_join` is never tried
again.

Shown (`test_f1_…`, and by hand): one recording, two runs it fits (same
puck, same pipeline, three seconds apart).

| How the two runs arrive | A1 | A2 |
|---|---|---|
| Both in one export (the build's B7 fixture) | `ambiguous` | `ambiguous` |
| A1, then A2 one export later | `certain`, with the recording's path | `ambiguous` |
| A2, then A1 one export later | `ambiguous` | `certain`, with the recording's path |

`voice_label_sheet.join` on the same rows and the same recording says
ambiguous for both. So the stored answer is not the join's answer, and
"ambiguous stored and never guessed" does not hold: whichever run arrives
first takes the recording as certain, and the row keeps that for good.

Why it is the usual case and not a corner: a run reaches Tempo three to
four minutes after it ends, each on its own clock, and the timer fires
every 60 s. Two runs 20 s apart land in different exports about one time
in three. The build's B7 test passes because all four of its runs arrive
in one export, which on the live system happens only in the first export,
where most rows are too old to be tried at all.

How often the precondition occurs: seldom. It needs one recording that
fits two runs and no second recording to pair off (a run whose recording
was never written, next to another run on the same puck). With two
recordings for two runs the answer came out the same either way (tried:
both orders, both `ambiguous`, as the join says). When it does occur the
dataset holds the wrong clip marked certain, and nothing re-examines it.

Smallest fix I can see: make the join when the row is final (the same
15-minute rule as the whole-trace read), when every neighbour that can
exist has arrived; the mutation run shows the existing B7 test would not
notice either way, so the fix needs `test_f1`.

Two smaller things in the same code, should-fix with it:

- A recordings directory that cannot be read when a run is first seen
  leaves `audio_join` NULL and it is never tried again (shown: directory
  moved away for one export, back for three more, still NULL).
- The six-day limit: see note 7 below.

## Should-fix

### 2. A nonsense trace-by-id answer crashes the run (B3 holds for searches only)

Where: `trace_spans()` and `_attrs()`; `export()` catches `TempoError`
only. Shown (`test_f2_…`, three shapes): `scopeSpans: 5`, `spans: 5`,
`attributes: 5` each raise `TypeError` out of `main()`: no status file, a
traceback in the journal, nothing written, and the same on every later
run while Tempo answers so. Thirteen other shapes (a string, a list, no
`trace`, no `voice.run` span and so on) are handled as a failed trace
read, exit 0, status fresh. The build's eight nonsense shapes are all
search answers. Graded should-fix and not a blocker because Tempo cannot
plausibly produce these three shapes and nothing is written wrong; by the
letter of B3 ("answering nonsense … exit 0, the status file carries the
reason") it is a miss, and the coordinator may read it harder.

### 3. Three traces that never read starve every older waiting row

Where: `export()`, the `want` list (`ORDER BY start_s DESC`) and
`TRACE_FAILS_MAX = 3`. Shown (`test_f3_…`): trace reads fail for one
export, so 20 rows wait; then all but the three newest read fine. After 40
more exports: 0 of 20 rows have `raw_trace`; the loop stops at the third
failure every time, before it reaches a readable one. The status says
`ok: true` with "3 trace read(s) failed … tried again next run". After
Tempo's 90 days the 17 readable rows have lost `raw_trace`, the engine,
the stage times, `window_cut_short` and the conversation id for good.
Needs a waiting backlog older than the failing three, so it follows an
outage of trace reads; in steady state newer rows are read first and are
not affected.

### 4. A watermark in the future loses the next day of speech; missing runs are only counted

Where: `export()`: `new_wm = max(wm, now - FINAL_S)`; reads start at
`wm - 3600`. Shown (`test_f4_…`): one export with the clock a day ahead,
then 20 runs over the next 20 hours with the clock right: the record took
0 of 20. The status says `ok: true`; the hourly check says "20 run(s) in
Tempo missing from the record" and takes none, by the criteria's "reports,
does not rewrite". Taking a missing run is an insert, not a rewrite, and
there is no command or documented step that takes one (the way back today
is setting `export_state.watermark_s` by hand, which the feature doc does
not say). The rows are recoverable for 90 days and then gone. A wrong
clock is rare here; the wider point is that "missing" has no remedy.

### 5. A lost record is started again, empty, and reported as ok

Where: `open_record()` creates the file when absent. Shown (`test_f5_…`
and by hand): a record of 7 rows, 5 of them older than Tempo holds;
the file removed; the next run: exit 0, `ok: true`, `last_error: null`,
a new record of 2 rows. `backups.py`'s warning "the voice-run record … is
missing, but its exporter has written voice_runs.json" fired with the
record gone and stopped firing after the exporter's next run, one minute
later (`[]`); the weekly copy then reads `ok, 0 runs`. The daily check
runs once a day and the exporter every minute, so that warning cannot
fire on the live system. From then on the weekly copies are of the new
record and the eight good ones rotate out in eight weeks. The record
should not be made again when a status file or a published copy says one
existed (a first export by hand, or a flag, makes it).

### 6. The feature doc's removal leaves the words in the record

Where: `docs/features/voice-dataset.md`, "Removing a run". Shown
(`test_f6_…`): a row that had been changed once (so its old row is in
`run_changes`), removed with the doc's statement: the row's words are
still in the record file, in `run_changes.old_row` (1 row), and the row's
`seq` is not raised. Also by reading: SQLite does not zero freed pages
(`secure_delete` is off), so the words can stay in the file's free pages;
and the eight weekly copies and the monthly tars made before the removal
keep them. The doc should give a removal that clears `run_changes` for
that run, and say what the backups still hold.

With it: a removal made while Tempo is down stays published (shown: the
row was still in the copy after the next run), because `main()` publishes
only after a good read. The publish depends on the record, not on Tempo.

### 7. The restore runbook installs the record under a running exporter

Where: `docs/runbooks/restore.md`, step 14; step 10 starts "every enabled
timer", which from the promotion on includes this one. By step 14 the
exporter has made an empty record and runs every 60 s; the block removes
the side files and `install`s over the file without stopping the timer.
Shown: the block as written, onto a target where the exporter had already
made a fresh record, gives the record back (`ok 5 1`, every run id and the
label; the exporter's next run adds the new run and keeps the label). So
the text works. What it leaves open is the exporter firing during the
`rm`/`install` pair (it would open a half-written file, or make a schema
in an empty one). Two lines fix it: stop the timer before, start it after.

### 8. The whole-window reads have no time budget

Where: the hourly check (91 searches) and the first read (182 searches
with its check) in `export()`; each request may take 5 s; the unit stops
the run at 50 s. Shown: a run with the hourly check and 6 ms a request
took 0.57 s, so at 0.6 s a request it takes about 57 s: systemd kills it
before the transaction, no status is written, `last_check_at` stays, and
every run after it tries the check again and dies the same way. B3's
"slow (10 s)" case is fine (the first request times out at 5 s and the
status says so); the hole is a Tempo that answers in half a second to
five. Live today the 90 searches take 0.26 s, so the margin is about a
hundred times.

### 9. A SQLite error inside the export leaves `main()` as a traceback

Where: `main()` catches `TempoError` around `export()`, nothing else.
Shown: the record held in a write transaction by a person's session past
the busy timeout: `OperationalError: database is locked` out of `main()`,
no fresh status. A full disk under the record takes the same path. The
record is untouched (the transaction rolls back); the page only sees a
stale status. The status file should carry the reason, as it does when
the record cannot be opened.

### 10. A failed enrichment is silent

Where: `voice_transcripts.fetch_runs` sets `_enrich_error`; the exporter
never reads it. Shown: a run with a Kronk trace id whose trace never
reads, exported for two hours: `rule` NULL, `ok: true`, `last_error`
null. After the 75 minutes a run stays in the read window the rule is
empty for good, and the hourly check reads without enrichment, so it
never reports it. Live today enrichment made 12 reads with no error.

## The build's eleven notes

1. **The stage filter `.*stt.*`.** Right. Both patterns count 113 on the
   live Tempo, and no run today starts with a wake stage, so the data
   cannot say whether `=~` is anchored; `.*stt.*` is right either way and
   the client-side check backs it (its removal is caught).
2. **`run_changes.detail`, `last_check_at`, `last_check`.** Right; the
   doc records them.
3. **A failed read writes nothing to the record.** Right, and it is what
   B3 says. It means the record never learns of a Tempo outage; the
   status file is the only place. Fine.
4. **`--status` repeatable.** Right.
5. **All three paths or none.** Right, and worth keeping: it is what
   stops a scratch run writing the real `data/`.
6. **`left_out_dev_text_runs` kept and NULL.** Right. A decision for the
   coordinator only if the column should go; it costs nothing.
7. **The join only for rows that ended less than six days before their
   first export.** The reason is right and NULL is the right value for
   "not tried". **A decision the coordinator has to make**, for two
   reasons. First, the cut is tighter than it need be: the archive moves
   recordings older than seven days on Mondays only, so recordings up to
   about two weeks old are local (today all 66, back to 2026-11-19, 13 of
   them from that day), and rows six to thirteen days old are skipped
   while their audio sits on disk. On the live system 60 of the 113 rows
   would get NULL on the first export, and more each day the promotion
   waits. Second, nothing ever tries those rows again (and see finding 1:
   the join's timing needs changing anyway). A pass that reads the NAS
   layout, or a retry of NULL rows while the recording can still be
   local, should be ordered or the gap named in the criteria.
8. **A change older than the one-hour overlap is only reported.** Right
   by the criteria. See finding 4 for the cost of "only reported" when
   the difference is a missing run.
9. **A removal does not raise `seq`.** Right as a fact (shown in
   finding 6's test: `seq` unchanged). **A decision for the coordinator
   in step C**: raising `seq` by hand would not help, since a removed row
   is not in the copy for `changed_after` to return. The page has to
   notice `meta.rows` or `content_sha256` changing, or reload the window.
   The removal recipe should say which.
10. **The two stale facts in `voice-capture.md`.** Right: `backups.py`
    moves at 7 days (`KRONK_ARCHIVE_AGE_DAYS`), and the recordings do
    leave the host.
11. **The search shape checks.** Right for the search. The same care is
    missing for the trace-by-id answer (finding 2).
