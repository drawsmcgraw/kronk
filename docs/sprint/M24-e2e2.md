## Findings

### Blockers

None.

### Should-fix

1. **A two-word opener is still spoken alone.** `_says_something` counts
   complete sentences of two or more words in all, so an opener of two
   words is enough to drop a long cut sentence after it. Function and app
   agree (speech mount, model faked, `finish_reason: length`, 16 cases
   each, `VOICE_STREAM` on and off, both lock modes):

   | Talkie's text | Old, spoken | New, spoken |
   |---|---|---|
   | `"Of course. The Presidents of the United States, in order, were Washington, Adams, … Jackson, Van Bu"` | `"Of course."` | `"Of course."` |
   | `"Certainly, sir. The Presidents …"` | `"Certainly, sir."` | `"Certainly, sir."` |
   | `"Certainly! The Presidents …"` | `"Certainly!"` | the whole text |

   Also "Very well.", "Yes. Indeed.", "I say!", "Ah! Oh!", "Why,
   certainly!". Not new: the old code did the same, and the fix closed the
   one-word case. Not seen live (0 of 13 here, 0 of 50 in the first test
   began with an opener). The cost is a spoken reply of two words with no
   error, which is what the ruling called a tenet 7 failure for one word.
   It is not silence and not a heading, so I do not grade it a blocker.
2. **The fix keeps a cut fragment where the old code spoke complete
   lines.** A unit counts only if it ends on ".", "?" or "!" (after
   closing quotes and brackets). When every complete unit before the tail
   ends some other way, nothing is dropped and the cut word is spoken. In
   the generated texts: 27,686 of 610,702 where the old code left content
   and the new one keeps the cut tail. Through the app, 16 cases each:

   | Talkie's text | Old, spoken | New, spoken |
   |---|---|---|
   | `"Washington\nAdams\nJefferson\nMadi"` | `"Washington.\nAdams.\nJefferson."` | `"Washington.\nAdams.\nJefferson.\nMadi."` |
   | `"Washington,\nAdams,\nJefferson,\nMadi"` | `"Washington,\nAdams,\nJefferson,"` | `"…Jefferson,\nMadi."` |
   | `"**The canal is fifty miles long.**\nIt was op"` | `"The canal is fifty miles long."` | `"The canal is fifty miles long.\nIt was op."` |
   | `"The canal is fifty miles long. --\nIt was op"` | `"The canal is fifty miles long. --."` | `"… --.\nIt was op."` |

   Also a line ending in ";", "…" or "[1]", a line of the form `1066:
   William I`, and a code fence. The fix report says a reply cannot get
   shorter, which is true; it does not say that some replies now end on a
   broken word that the old code removed. Nothing is lost and nothing is
   silent, so the cost is low. The first test saw one live reply end
   " --."; a one-name-a-line list is the likeliest way to meet this.

### Notes

1. Two tables that have a header and no rows, one after the other, count
   as a table with a row (`rows >= 2` counts the second header). A capped
   reply of that shape is spoken as its headers alone ("King, Year. King,
   Year."): the 31 and 7 in the job 1 table. Same in the old code. Talkie
   has written no markdown in 63 live replies, so I grade it a note; read
   strictly it is "a heading alone".
2. A list item with nothing after its marker counts as an item
   (`"Certainly:\n\n- \n- Wil"`). Here the new code drops nothing, so
   nothing is lost.
3. "the Rt. Hon" loses "Hon" and is spoken "the Rt." in both trees: the
   sentence splitter takes "Rt." before a capital for a sentence end. The
   first test's note 6 covers this family.
4. `"**The canal is fifty miles long.** It was op"` (the emphasised
   sentence and the cut on one line) is kept whole in both trees: no unit
   boundary falls after the closing "**".
