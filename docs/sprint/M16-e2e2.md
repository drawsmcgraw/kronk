## Findings

Severity: blocker, should fix, note. Paths were under `/tmp/kronk-m16-e2e2`
(removed). Every archive case ran the real `scripts/backups.py` with the
real `alpine:3.20` delete on root-owned trees unless it says otherwise.

### Blocker

**1. A destination copy rewritten in place after its verify is not noticed;
the local file is deleted and the run reports OK.** Blocker by the brief's
definition; narrow.
Reproduce: `run1/01_a.wav` (4,000 bytes) and `run2/01_b.wav`, both old.
After the copy of `01_a.wav` is verified and before the delete batch (I
injected it at two points: before the host's re-check and before the
container starts), overwrite the destination copy's bytes in place: same
inode, same size, other content. Result on both placement paths: `Moved 2
recording(s)`, exit 0, result `ok`; locally nothing; the destination holds
the overwritten bytes; the recording's content exists nowhere.
Cause: at delete time the destination copy is checked by size and
device:inode only (`dest_copy_problem` and the `d=$(stat -c '%s %d:%i' …)`
line of `DELETE_SCRIPT`); its content and its mtime are not looked at. The
same rewrite with a new inode, a truncation, a removal, a symlink and a
swapped directory are all caught.
Reach: something must rewrite a just-verified file on the share in place
within the batch window (seconds, or minutes when a large file is in the
batch). Nothing in Kronk does. A rewrite one second after the delete would
lose the same recording and no archive job can prevent that, which is the
argument for a lower severity; the argument for this one is that the job
does look at the copy again at that moment and the feature doc says "a
swapped, changed or vanished file, on either side, is kept".
Fix: in `DELETE_SCRIPT`, hash the destination copy too (`sha256sum < "$t"`,
compared with the hash already passed in; the destination is mounted
read-only in the container) or at least compare its mtime (`%Y`, which the
copy sets to the recording's); a test that rewrites the destination copy in
place between `copy_verified` and `remove_recordings`.

### Should fix

**2. The rename fallback has no test, and it is the path the real share may
take.** Three mutants of it pass all 125 tests: the fresh check before the
rename removed (the rename would then replace an existing file), `EPERM`
dropped from the errors that select the fallback, and the rename itself
removed. I ran the full archive table on that path by hand (below) and it
held; `EOPNOTSUPP` and `ENOSYS` from `link` also take it; `EACCES` and `EIO`
end as "cannot put the copy in place", file kept, temporary file removed.
Fix: tests that make `os.link` raise `EPERM`: a plain move, a final name
that already exists, and the placed file's inode check.

**3. When `<dest>/recordings` is gone at delete time, Docker creates it:
empty, root-owned, 0755.** The delete container is started with `-v
<dest>/recordings:/dst:ro`, and `docker run -v` creates a missing source
directory. Reproduced by removing or renaming `dest/recordings` after the
verify: every delete is refused and nothing is lost, but the directory is
back, owned by root. On the real share, a lazy unmount in the middle of a
run would put that empty directory on the local disk under
`/mnt/nas-backup`, which is a write to an unmounted default destination
(not reproduced on a mount: no root here). Fix: `--mount
type=bind,source=…,target=…[,readonly]` for both mounts, which fails when
the source is missing.

**4. One production tag that is not a local ref takes the whole bundle
out, and the run is still OK.** The bundle's refs are HEAD, the branch and
every release directory name Docker reports for compose project `kronk`. In
a scratch repository without those tag names: `unpushed bundle: NOT WRITTEN:
git bundle failed (128): fatal: ambiguous argument 'sprint-M17'…`, no bundle
member, title `config backup OK`, exit 0, and the notice body carries git's
multi-line usage text. It is said, not silent, and today both tags exist.
Fix: `git rev-parse --verify` each tag before adding it; first line of the
error only.

**5. Defaults and three behaviours are unpinned** (mutants below): the
archive age of 7 days, the 12 tars kept and the 35 stale days can each be
changed with no test failing; a symlinked directory inside a backed-up tree
can be dropped or followed; a symlink in HA's tar stream can be dropped;
the SQLite online backup can be replaced by a raw read of the file.

**6. Runbook.** (a) Step 4 ends with `sudo reboot`; `$T`, `$R` and `$K`
from "Conventions" are gone afterwards and nothing says to set them again.
(b) "Restore one thing" writes `~/restore/ha-storage-before-restore.tgz`
(HA's auth store) and says it "goes with step 16", but step 16 removes only
`~/restore/kronk-config-<date>`.

### Notes

7. **A killed run can leave two things outside the destination.** A
   SIGKILL while a helper `docker run` is being created left a container in
   state `Created` (image `alpine:3.20`, `/etc/kronk` read-only, never
   started, so `--rm` never fired), and one while the bundle was being
   written left `/tmp/kronk-bundle-*` (0700, code only). Seen once each in
   15 timed kills; both removed by me. Nothing cleans them up.
8. **The rename fallback's window is real.** With a file created under the
   final name between the fresh check and the rename (injected), the rename
   replaced it. Documented as residual in the fix report. No second writer
   exists while the lock is held. `renameat2(RENAME_NOREPLACE)` first, where
   the filesystem supports it, would close it.
9. **`solar.db` and `music_taste.db` are optional.** With `solar.db`
   unreadable (a corrupt file) the tar is `OK … NOT READ`, exit 0, and
   counts toward retention. They are the only copies of household data in
   the tar; consider making them required.
10. **Nothing left on the destination is ever cleaned.** Each killed archive
    run can leave one `.kronk-archive.<pid>.<hex>.tmp` (counted in the
    notice's "N files" and named in its last sentence), and each incomplete
    config run leaves an `.incomplete` tar that retention never removes. By
    design; they accumulate until a person deletes them.
11. **A replaced local file becomes a permanent conflict.** After the first
    report's blocker 2 scenario the replacement stays local and every later
    run ends FAILED ("a different file of the same name (both kept)") until
    a person renames one. That is criterion 8's rule.
12. **`Persistent` catch-up inside the upgrade window**: a run that starts
    at boot while the upgrade run holds its lock waits 30 minutes, declines
    (exit 3) and is not retried until its next date; the 09:30 check
    reports the declined run. No deadlock is possible: `upgrades.py` and
    `deploy_tag.sh` never look at the backup lock, and the backup only
    probes the upgrade lock without blocking while it holds its own.
13. **The bundle note names the refs asked for, not the refs in the
    bundle**: "(HEAD, refactor, sprint-M17, sprint-M18)" while the bundle
    holds HEAD, `refactor` and the `sprint-M17` tag object; `sprint-M18` is
    recreated with the `git tag` line `repo-state.txt` gives (done: same
    commit as live).
14. **Wording.** "1 commits not pushed". The feature doc's "the recordings
    directory and `<dest>/recordings` read-only mounted" reads as if both
    were read-only; only the destination is. The same paragraph's "changed
    … on either side" is not true for finding 1.
15. **Still open until the first real mount** (not testable here): whether
    the Synology takes `link(2)` or the rename path; that `fchmod` and
    `utime` on the temporary file succeed on CIFS (a failure there would
    fail every copy, loudly); `serverino` inode stability (deletes are
    refused, not blind, without it); that the read-back shows as reads in
    `/proc/fs/cifs/Stats`. A watched first run on one old recording would
    settle all four.
16. **A sparse file is copied dense** (the 30 GB sparse file was refused as
    "destination full" on the 4 MB tmpfs, and smaller files still went).
17. **Tester's breaches and leftovers.** (a) For the step-11 order test I
