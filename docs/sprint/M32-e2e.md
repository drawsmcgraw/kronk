## Should fix

### S1. A burst of writes leaves the path unit failed for good

`kronk-work-export.service` has systemd's default start limit, 5 starts
in 10 s (`systemctl --user show`: `StartLimitBurst=5`,
`StartLimitIntervalUSec=10s`; the live unit has the same). The path unit
starts it on every write. On scratch copies of both units (the path
unit's text with only the two names and the path changed; the service
with `--db <scratch> --out <scratch>`), after five single writes four
seconds apart, ten writes in 0.56 s:

```
m32test-work-export.service: Start request repeated too quickly.
m32test-work-export.service: Failed with result 'start-limit-hit'.
Failed to start m32test-work-export.service - m32test scratch copy of kronk-work-export.service.
m32test-work-export.path: Failed with result 'unit-start-limit-hit'.
```

The path unit was then `failed` and stayed so: the next nine bursts and
thirty writes at once started no export (0 runs each), and the output
still showed a write from the middle of the first burst. A start of the
service by hand after the ten seconds worked; the path unit did not come
back with it. Nothing on the page says so: on the live system the timer
would go on, and every write would wait up to a minute again, silently,
until someone restarts the path unit. Six starts inside ten seconds is a
coordinator's chain of `work.py` commands at a promotion, or an agent's
launch beside it.

With `StartLimitIntervalSec=0` in the scratch service's `[Unit]`, ten
bursts of ten writes each started 5 exports and each ended with its last
write exported; three rounds of ten writes at once started 2 each and
ended equal to the database. That is a change to the live service file,
which the timer shares, so it is the coordinator's to choose; a limit on
the path unit or a debounce would do as well. A second scratch run showed
a timer whose service hits the limit keeps running (its starts inside the
window are refused, then it goes on), so the 60 s timer itself is not at
risk. `tests/test_m32_e2e.py`, strict `xfail`.

### S2. Twenty pages hold the orchestrator on the 2% line

Second run, nothing else of mine polling dev, 06:41:05 to 06:51:09, the
page as served, 3,998 polls (396 to 398 a minute), 400 "Heard" requests:

- by the container's cgroup counter: 12.46 CPU-seconds in 604.3 s, a
  mean of **2.06%** of one core. The same container with no page open,
  90 s before: 0.66%.
- by `docker stats`, 67 samples: median **1.28%**, mean of the samples
  1.74%, 12 samples over 2%, the highest 8.23%.

The samples over 2% are the seconds after the file changes: each of the
twenty pages then gets the whole answer (127 KB), and the route encodes
it twenty times (200 whole answers in the window, ten changes). Keeping
the encoded body with the parsed file would take most of that away. The
first run (06:18:30 to 06:28:34) had a page of my own 500-update test
pulling the whole file every 3 s beside it: median 1.51%, mean of the
samples 2.31%, 26 of 67 over 2%.

I count the criterion met by the method the brief names (`docker stats`,
sampled); by the exact mean it is 0.06 over. The coordinator may read it
the other way.
