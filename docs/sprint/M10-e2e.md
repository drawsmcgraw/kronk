## Observations that are not failures

**O1. A live "pass" means the right lane and the right tool, not the right
music.** The replay compares tier, rule, tool, and, only when `tool_service`
logged a `music dry run:` line, the action and the speaker. It does not
compare the name, media type or provider, and it does not look at whether the
request succeeded. In my run three rows passed while the answer was wrong:

- `plan-orbital-station-youtube` (a plan-named utterance): "I couldn't play
  that. I couldn't find a station called orbital radio station in Music
  Assistant. The closest I found was Orbital Radio." Trace
  `4d161836aef4848d0fa78c3944a022da`.
- `eval-shuffle-the-anime-bangers-playlist-on-sonos`: "I couldn't find a
  playlist called anime bangers playlist … The closest I found was Anime
  Bangers." Trace `cda576f7673e192c0fd663f505fe43e3`.
- `eval-stop-sonos-move-derp`: expected the Sonos Move; the answer was "The
  Office speaker is already paused." No dry-run line is logged when nothing
  is playing, so the speaker check did not run. Trace
  `c094d9607752c0ac0152a787d7046518`.

The feature doc states what is checked, so this is disclosed, and criterion
10 is met as written. It matters because plan change C5 makes this replay the
main evidence for the M11 cutover. Before that, a fix agent should add two
checks to `compare_kronk`: a play row whose `/music` call returned an error
is a failure unless the row is tagged `no-such-item`; and the resolved name
and media type in the dry-run result are compared with `expect.name` and
`expect.media_type`. The dry-run response already carries them.

**O2. Half the corpus never reaches Kronk in the live layer.** 66 rows are
checked read-only, 57 of them sentence triggers. For those the replay proves
only that HA would take the sentence; 33 of the 57 do not even assert which
trigger. Five of the plan's ten named utterances are in this group (Anime Pop,
The Girl with the Sun, shuffle anime bangers, put on some jazz, the ninety's
station), so their music outcome is not exercised by any layer today. The
build report says this (deviation 3). It stays true until either
`prefer_local_intents` or the blueprint changes on the dev path, or M11's
parser test covers them offline.

**O3. Hey Jarvis is not a dev wake word for music.** Check (e). Until the
blueprint's `kronk_agent` follows the pipeline, or the dev pipeline stops
matching triggers, a spoken "Hey Jarvis, play …" is a production play. Drew's
decision, already listed in the build report.

**O4. Notes for the M11 agent on the parser hook.**

- The hook compares with `!=`. Many rows state the resolved item, not the
  words: `"Pink Floyd"` for "play pink floyd", `"Destiny Waiving"` for a
  sentence that says "Destiny Waving", `"90s, 2000s, Today's Hits Radio"` for
  "ninety's two thousands and today's hits", `"anime bangers"` for "Anime
  Bankers", a Sonos entity id for "Sonos Move Dirt". A parser that returns
  what was said will fail these rows on case and spelling alone. M11 has to
  decide whether the hook tests the parser or parser plus resolver, and
  normalise accordingly.
- `eval-play-the-albo-daisies-of-the-galaxy` expects `artist: "Eels"`; the
  sentence does not name an artist. It sits under a `parser` marker for a
  different reason (the "Albo" mishearing).
- `plan-girl-with-the-sun` carries a strict `parser` marker whose reason says
  M11 will get it right. The day the parser lands and does, the suite fails
  with XPASS until the marker is removed. That is the tripwire working, but
  expect it.

**O5. "Late evening from Radio on Pandora." would create a Pandora station on
a real play.** Both replays answered "Dry run: would play the Pandora station
Late Evening Radio, made new …". `created` is set when Music Assistant's
`music/item_by_name` returns a `seed:` item (`tool_service/main.py`,
`_pandora_station`), meaning a catalogue station the account does not have,
which the provider creates on first play. Nothing was created: the lookup is
a read, the dry-run gate returns before `play_media`, the second replay still
got a `seed:` item, and Music Assistant's log for the replay window holds
only websocket authentication lines (42). But the 2026-11-07 incident doc
says no request path creates a station any more. Either the Pandora
`offer_new_stations` setting is on again or `item_by_name` ignores it. Worth
one read-only look at Music Assistant's setting by the coordinator or Drew. I
did not query Music Assistant's settings.
